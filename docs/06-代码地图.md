## 二、一次请求的完整旅程

以「打开控制台」为例：

```
浏览器 GET /dashboard
  │
  ├─ ① src/proxy.ts（106 行）
  │     两件事：
  │       1. 路径上带 ?code= 就转去 /auth/callback（魔法链接兜底，
  │          见铁律三下面的附注）
  │       2. 刷新 Supabase 会话 cookie
  │     ⚠ 这里【不】做鉴权判断 —— 见下面铁律三。
  │
  ├─ ② src/app/(app)/layout.tsx（27 行）
  │     只渲染页面壳（顶栏 + 底部 tab 栏）。同样不做鉴权。
  │
  ├─ ③ src/app/(app)/dashboard/page.tsx
  │     const user = await requireUser();        ← 鉴权发生在这一行
  │     const today = todayInTimezone(user.timezone);
  │     四个查询用 Promise.all 并发跑
  │
  ├─ ④ src/lib/auth.ts → getCurrentUser()
  │     读 cookie → Supabase 校验 → 返回 SessionUser（含 timezone）
  │     未登录时 requireUser() 直接 redirect('/login')，下面的代码不执行
  │
  ├─ ⑤ src/db/queries.ts → getDailySummaries(user.id, from, today)
  │     注意签名：第一个参数永远是 userId，由调用方传进来
  │
  ├─ ⑥ src/db/index.ts → withUser(user.id, async (tx) => { ... })
  │     开事务 → set_config('request.jwt.claims', {sub: userId}, true)
  │            → set local role authenticated
  │     ⚠ 这一步是安全模型的支点，见铁律二
  │
  ├─ ⑦ Postgres（Supabase）
  │     两道门依次检查：
  │       GRANT  —— authenticated 角色能不能碰这张表（缺了报 42501）
  │       POLICY —— 这个 JWT subject 能看见哪些行（缺了静默返回 0 行）
  │
  └─ ⑧ 回到页面组件，纯函数加工
        src/lib/nutrition.ts 里的 movingAverage / analyzeTrend ...
        最后渲染成 JSX
```

**关键点**：第 ⑥ 步之后，应用层**不再写 `where user_id = ?`**。越权由数据库兜底。
这样即使某天漏写一个条件，也只会查到空行，不会查到别人的数据。

**分层的规矩**（改代码时按这个找位置）：

| 想改什么 | 落在哪 | 不要落在哪 |
|---|---|---|
| 视觉、间距、颜色 | `globals.css` + 组件 className | 不要写内联 style |

| 表结构 | `db/schema.ts` + 一个新的 `drizzle/000N_*.sql` | 不要只改一边 |

## 四、三条铁律

这三条不是风格偏好，是**踩过坑之后定下来的**。每条都有对应的守卫。

### 铁律一：每个写操作，第一件事是 `requireUser()`

顺序很重要 —— 是「先验身份，再解析参数」，不是反过来。

```ts
export async function logWeight(raw: unknown): Promise<LogWeightResult> {
  const user = await requireUser();     // ← 第一行
  const parsed = schema.safeParse(raw); // ← 第二行
  ...
}
```

**为什么**：如果先解析参数，未登录的请求也能触发参数校验逻辑，等于把内部结构暴露给匿名调用者。
`requireUser()` 在未登录时直接 `redirect('/login')`，后面的代码根本不执行。

**守卫**：`tests/verify-server-actions.mjs` 扫描所有 `'use server'` 文件，确认导出的都是 async 函数。

### 铁律二：数据访问一律走 `withUser()`，不在应用层写 `where user_id`

```ts
await withUser(user.id, async (tx) => {
  // 这里没有 where user_id = ...
  // RLS 会按 request.jwt.claims.sub 过滤
});
```

**为什么**：平时连库用的 `postgres` 角色是表属主，**直接绕过 RLS**。
如果业务查询都用它跑，那 RLS 策略写了等于没写 —— 测试全绿，
但线上任何一处漏写的 `where` 就是全量数据泄露。

**注意 `set_config` 的第三个参数必须是 `true`**（只在本事务内生效，等价于 `SET LOCAL`）。
写成 `false` 会留在连接上 —— 而连接要还回池子给下一个请求复用，
于是「张三的身份」会泄漏给「李四的请求」。这类 bug 只在并发下偶发，
本地单线程测试永远测不出来。

**守卫**：`tests/verify-migrations.mjs` 在内存 Postgres 上跑真实迁移，
模拟 `authenticated` 角色断言跨用户不可见。

### 铁律三：`proxy.ts` 和 `layout.tsx` 里**不**做鉴权

```
src/proxy.ts            → 刷新会话 cookie + 把落错路径的 ?code= 转去 /auth/callback
src/app/(app)/layout.tsx → 只渲染页面壳
各页面的 page.tsx        → 在这里 requireUser()
```

**为什么**：Next.js 的 `layout` 在客户端导航时**不会重新执行**。
把鉴权写在 layout 里，用户退出登录后仍能看到页面壳 ——
看起来像没退成功，实际是 layout 没重跑。所以校验放到每个页面里。

**代价**：每个受保护的页面都要写一行 `await requireUser()`。忘了写 = 页面裸奔。

**守卫**：`npm run auth:verify`（`tests/verify-auth-boundary.mjs`）——
真的起一个生产服务，发**不带 cookie** 的请求，断言 5 个受保护路径返回 307 且指向 `/login`，
同时断言公开路径仍然打得开（不能修成「锁死所有人」）。

> 这个守卫是写这份文档时才补上的。当时发现 `db:verify` 和 `db:verify:hosted`
> 全是数据库层断言 —— 它们证明「数据库不会把别人的行给我」，
> 但证明不了「未登录的请求打不开这个页面」。这两件事是独立的：
> RLS 再严，只要某个 `page.tsx` 忘了写 `requireUser()`，那个页面就是公开的，
> 而且返回 200，从外面看毫无异常。
>
> **这个错误没有任何别的机制能拦住** —— typecheck 不知道哪些页面该受保护，
> eslint 不知道，数据库层的断言也看不到 HTTP。只能真的起服务发一次请求。
>
> 加新页面时记得往 `tests/verify-auth-boundary.mjs` 的 `PROTECTED` 数组里补一行。

### 附：魔法链接为什么会在配置不对时**静默**失效

这是本项目遇到过的最难查的一个失败模式，值得单独记一笔。

Supabase 在发信前会检查 `emailRedirectTo` 是否在项目的 **Redirect URLs** 白名单里。
如果不在，它**不报错**，而是悄悄把回跳目标替换成项目的 **Site URL**。
于是真实邮件里那条链接会把用户打到

```
https://<域名>/?code=xxxxxxxx
```

—— 一个没有任何代码处理 `code` 的地址。表现是「点完链接还是没登录」，
服务端日志里一条错误都没有。配置错了一格，症状却像「产品坏了」。

两层防线：

1. **配置层**：Site URL 与 Redirect URLs 都配好 —— 具体路径见
   [docs/05-部署.md](05-部署.md) 的 1.1 节。
2. **代码层**：`src/proxy.ts` 看到任何路径上带 `code` 就转去 `/auth/callback`。
   配对了它不介入，配错了它救命。配置是外部状态，会漂移、会被改错、会在换域名时忘掉，
   只靠配置等于把「能不能登录」交给一个没人 review 的网页表单。

只认 `code`、不认 `error` 是有意的：`/auth/callback` 出错时会跳
`/login?error=exchange`，如果这里也转发 `error`，就成了无限重定向。

### 附：`'use server'` 文件只能导出 async 函数

这条踩过一次，代价是线上登录接口 **500**。

```ts
'use server';
export const LOGIN_INITIAL = { ... };   // ❌ 整个文件在运行时报错
export async function sendMagicLink() { }  // ✅
```

Next.js 要求这类文件里的**每一个导出**都是 async 函数。混进一个对象或常量，
报错是 `A "use server" file can only export async functions, found object.`，
而且**开发模式下页面正常，只有真正提交表单时才 500**。

状态常量要放在旁边的 `state.ts` 里（`login/state.ts`、`settings/state.ts`、
`onboarding/state.ts` 就是这么来的）。

**守卫**：`npm run actions:verify`，同时检查「有没有非法导出」和「导出的 action 有没有人调用」。

## 五、加一个新功能要动哪些文件

用真实例子讲 —— 这是「记录体重」功能的完整改动清单（提交 `b3a64c8`，5 个文件 274 行）：

| 顺序 | 文件 | 做什么 |
|---|---|---|
| 1 | `drizzle/000N_*.sql` + `drizzle/meta/_journal.json` | 需要改表结构时才动。**这次不用** —— `measurements` 表早就有了 |

## 六、五层检查（`npm run verify`）

```
typecheck  →  tsc --noEmit                        类型
lint       →  eslint                             风格与常见错误
test       →  node --test tests/*.test.ts         52 项营养计算 / 时区 / 份量换算单测
actions:verify → 扫描 'use server' 文件            非法导出 + 死代码
db:verify  →  在内存 Postgres 上跑真实迁移          74 项断言（RLS、触发器、级联、迁移幂等）
```

命令：`npm run verify` = 上面全部串起来，**exit 0 才算过**。

还有两层**刻意不进 `verify`**（都需要额外前提，混进日常检查就会变成噪音）：

```
npm run db:verify:hosted  →  连真实 Supabase 跑 17 项断言（RLS 隔离、级联删除）
npm run auth:verify       →  起生产服务，发不带 cookie 的请求，断言鉴权边界（10 项）
```

为什么分开：

- `db:verify:hosted` 会真的连线上库、建临时账号、写数据、再删掉。
  放进日常检查，某天网络抖动就会让「验证」失败，久了就没人信这个命令了。
- `auth:verify` 需要一份生产构建产物（`next build`，约 40 秒）并占用一个端口。
  改了代码就得重新构建，否则测的是旧产物。

`auth:verify` 的用法：

```bash
NEXT_DIST_DIR=.next-build npx next build   # 先构建
npm run auth:verify                        # 再验
```

**写断言的两条纪律**（都是踩过坑换来的）：

1. **证明它真能抓到。** 新加一条断言后，把被测的修复临时改回去，确认断言变红。
   否则你写的可能是一条永远绿的断言（`verify-migrations.mjs` 里【I】节就有一条跑了很久的空断言 ——
   它建的用户恰好没有体重记录，而它断言的正是「体重记录被删干净」）。
2. **别用「有没有报错」判断写入被没被拦。** RLS 缺 POLICY 的表现是**静默返回 0 行，不报错**。
   必须断言 `count === 0`，不能断言「没抛异常」。

## 七、「反直觉但必须这样写」清单

这些地方看起来可以更简单，但简化会引入真实 bug。改动前先读那一段的注释。

| 位置 | 反直觉之处 | 简化会怎样 |
|---|---|---|
| `src/db/index.ts:43` | `prepare: false` | Supavisor 事务池下报 `prepared statement "s1" already exists`，且只在生产偶发 |
| `src/db/index.ts:93` | `set_config(..., true)` 第三个参数 | 身份泄漏给下一个复用连接的请求 |
| `src/db/index.ts:83` | 用 `db.transaction()` 而不是 `sql.begin()` | 后者回调里 drizzle 会抛 `Cannot read properties of undefined (reading 'parsers')` |
| `src/db/queries.ts` `getMealsForDate` | 用 `LEFT JOIN` 而不是 `INNER JOIN` 取份量 | `serving_id` 是 `ON DELETE SET NULL`，INNER JOIN 会让历史记录凭空消失 |
| 各页面 `dynamic = 'force-dynamic'` | 不能静态化 | 构建时烤死数据，第二天打开还显示昨天的 |
| `meal-logger.tsx` 的「改」按钮 | 用 `after` 伪元素扩触控区 | 直接加 `.touch-target` 会把 17px 的行撑成 44px，列表排版散架 |
| `src/proxy.ts` | 不在这里鉴权 | 见铁律三 |
