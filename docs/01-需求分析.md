# 01 · 需求分析

> 项目代号：**Slim**（暂定，可改）
> 一句话定位：一个苹果发布会审美、手机优先、能真实部署上线的「体重 + 饮食」可视化管理网站。
> 状态：**v1.0 已定稿**（2026-10-16 决策确认，见 §9）

---

## 1. 这个项目要同时满足两个目标

需求方同时是**产品使用者**和**学习者**，所以验收标准是双轨的。

| 轨道 | 目标 | 验收方式 |
|---|---|---|
| A. 产品轨道 | 真的有人天天用它记录减脂 | 连续 14 天，每天至少完成 1 次体重或饮食记录 |
| B. 学习轨道 | 走通"需求→设计→开发→部署"全链条 | 每个阶段有一份可讲解的产出物，能对着代码讲清每个决策 |

**已确认节奏（Q5）**：**边做边讲透，不追求速度**。每个技术点要展开讲"为什么这么设计、替代方案是什么"，文档要能当学习材料回看。

**推论**：不能用黑盒 BaaS 一键生成绕过流程。技术选型要在"省事"和"学到东西"之间取平衡——可以少写胶水代码，但不能看不懂数据怎么流动。

## 2. 用户画像

### 主用户：需求方本人
- **身份**：计算机专业研究生，有编程基础，**没有全栈部署经验**
- **健康状态**：健身小白、减脂新人，刚起步
- **设备**：Mac（开发）+ iPhone（日常记录）——**90% 的记录动作发生在手机上**
- **使用时机**：
  - 早上起床后、空腹、上完厕所 → 记体重（**10 秒内完成**）
  - 三餐吃完 → 记饮食（**每餐 30 秒内完成**）
  - 晚上睡前 → 看一眼今天热量超标没有
- **真实心理**：刚开始热情高，2 周后如果记录太麻烦就会放弃

### 次用户：1-2 个朋友（**已确认要做，P0**）
- 各自独立账号，**互相看不到对方数据**
- 需要：注册页、邮箱验证、密码找回、数据完全隔离
- **必须在第一天就做对**：所有表带 `user_id`，数据库层用 RLS 强制隔离。后期再补是灾难性的

### 非目标用户
- 健身教练、营养师（不需要专业工具链）
- 需要社交/排行榜的泛用户（不做社区）

## 3. 核心痛点（决定了功能优先级）

| # | 痛点 | 后果 | 对应功能 |
|---|---|---|---|
| P1 | 减脂新手**不知道该吃多少** | 盲目节食或吃太多 | 目标计算器：BMR → TDEE → 热量缺口 → 三大营养素目标 |
| P2 | **记录太麻烦** | 2 周后弃用 | 常用食物、最近常吃、一键复用昨天、组合餐模板 |
| P3 | 体重**每天在波动**，看不出趋势 | 掉 0.5kg 就焦虑，涨 0.5kg 就崩溃 | 7 日移动平均线 + 趋势解读，弱化单日数字 |
| P4 | **不知道吃的和体重有什么关系** | 无法调整策略 | 热量摄入 vs 体重趋势叠加图 |
| P5 | 缺乏正反馈 | 没动力坚持 | 进度环、连续记录天数、里程碑 |
| P6 | 数据散在备忘录/Excel 里 | 无法聚合分析 | 统一数据库 + 日历热力图 + 导出 |

> **产品判断一**：P2（录入效率）和 P3（趋势而非单日）是这类应用**成败的分水岭**，不是"以后再优化"的细节。
>
> **产品判断二（有实证支撑）**：JMIR mHealth 2026 年的研究结论是 "All calorie-counting apps saw a decline in adherence over time" —— **所有**热量记录 App 的依从性都随时间下降（[原文](https://mhealth.jmir.org/2026/1/e64139/)）。所以设计目标不是"功能全"，而是**降低第 30 天之后的录入摩擦**。
>
> **产品判断三（差异化立足点）**：调研的 13 个开源项目里，**没有一家把"体重"和"饮食"两块数据在 UI 上打通**（wger 分属两个 app，FitTrackee 无饮食，Grocy/Tandoor 无体重）。而"热量缺口 vs 实际体重变化"这条关联曲线，恰好是这个项目最该主打的图表。

## 4. 功能范围（MoSCoW）

### P0 · MVP

**F1 账号与认证（多用户）**
- 邮箱 + 密码注册/登录；邮箱验证；密码找回（魔法链接最省事）
- 首次登录引导：身高/体重/年龄/性别/活动水平/目标体重
- **数据完全隔离**：数据库层 RLS 强制，不只靠 API 层过滤

**F2 个人档案与目标计算**
- 输入：性别、年龄、身高、当前体重、活动系数、目标（减脂/维持/增肌）、期望速度（kg/周）
- 计算：BMR（Mifflin-St Jeor）→ TDEE → 建议缺口 → 每日目标热量 + 三大营养素克数
- 安全钳制：缺口上限、热量下限、速度上限（详见 `research/04-营养计算依据.md`）

**F3 体重记录**
- 日期 + 体重(kg) + 可选体脂率 + 可选备注 + 可选测量时间
- 同一天重复记录 → 覆盖（`UNIQUE(user_id, log_date)` + `ON CONFLICT DO UPDATE`）
- 列表 + 编辑 + 删除

**F4 饮食记录**
- 按餐次分组：早餐 / 午餐 / 晚餐 / 加餐（**默认餐次按当前时间自动判断**）
- 搜索食物库 → 选食物 → 输入克数 → 自动算热量与三大营养素
- 支持自定义食物

**F5 食物库**
- 内置 **100-300 条**常见中式食物 + 常吃外卖（自建，理由见 ADR-006）
- 字段以**每 100g** 为基准：热量、蛋白、碳水、脂肪、常见份量、分类
- 客户端模糊搜索（弱网零延迟）

**F6 仪表盘（"苹果发布会感"的主战场）**
- 今日热量：环形进度（已摄入 / 目标 / 剩余）
- 三大营养素：三条进度条
- 体重趋势：7 日移动平均主线 + 原始散点 + 目标线
- **热量 vs 体重：双轴叠加图（核心差异化）**
- 关键数字卡：当前体重、距目标差多少、本周平均热量

**F7 历史视图**
- 日历热力图（打卡密度）
- 点某天进入当日详情

**F8 数据导出**
- 一键导出 CSV（体重 + 饮食），**防止数据被锁死**

**F9 训练记录**
- 有氧：跑步机、爬楼机、台阶机、椭圆机、动感单车、划船机、跳绳、户外骑行、户外慢跑、跑步机快走
- 无氧：胸 / 肩 / 背 / 腿四个部位，共 58 个动作，每个动作标出**主要发力肌群**与**次要参与肌群**
- 每个动作两张定格照片来回淡入（示意起止位置），另配一张绿身红肌的人体图
- 记一次 = 选项目 + 时长 / 组数 + 次数 + 重量（重量留空 = 自重）

### P1 · 第二阶段
- 常用食物 / 最近常吃 / 一键复制昨天
- 组合餐模板（"我的固定早餐"）
- 目标到达日期预测（基于趋势斜率）
- 围度记录（腰/胸/臀/臂/腿）、体脂率趋势
- 进度照片对比
- PWA 完善：离线可用、启动图
- 每周复盘报告页

### P2 · 以后再说
- 条码扫描（iOS Safari 无原生 `BarcodeDetector`，需 zxing-wasm）
- Apple 健康 / 智能体脂秤数据同步
- AI 拍照估算热量（误差 ±30%+）
- 社交/排行榜

### 明确不做
- 运动训练计划与动作库（那是 wger 的领域）
- 社交社区、内容资讯、商业化

## 5. 关键交互场景（用户故事）

**US-1（早上的 10 秒）**
> 我早上称完体重，打开手机上的网站，首页直接有一个大号数字输入框。我输入 `68.4`，点确认。页面给我一个轻微的正反馈（数字滚动 + 趋势线动了一下），我就关掉了。

*设计要求*：首页直达，不需点进二级页面；输入框自动聚焦、`inputmode="decimal"` 唤起数字键盘。

**US-2（午饭后 30 秒）**
> 我吃完食堂的鸡腿饭，打开"饮食"页，**默认已经停在"午餐"**。搜索"米饭"，选 200g；搜索"鸡腿"，选 150g。顶部环形进度条实时更新。

*设计要求*：默认餐次按当前时间自动判断；搜索即输即搜；常用食物排在最前。

**US-3（晚上看一眼）**
> 我晚上 10 点打开首页，看到今天剩 320 kcal，蛋白质还差 40g。我决定喝一杯蛋白粉。

*设计要求*：一眼看懂"还能吃什么"，而不是给一堆数字。

**US-4（第 10 天有点慌）**
> 我连续记了 10 天，体重从 70.0 到 69.6，中间还涨过。我打开趋势图，看到 7 日均线在稳定下降，心里稳了。

*设计要求*：默认展示均线；单日数据点弱化；给一句人话解读（"本周均线下降 0.3kg，符合每周 0.5% 的健康速度"）。

**US-5（朋友加入）**
> 我把网址发给朋友 + 给他一个邀请码，他自己注册，看不到我的任何数据。我也看不到他的。
>
> （2026-10 补：当时验收句写的是「他自己注册」。后来发现「知道网址就能注册」是个只靠运气守着的口子，于是加了邀请码 —— 判据从「他有网址」变成「我给了他一个码」。）

*设计要求*：RLS 在数据库层强制；前端任何页面都不能泄露他人数据。

## 6. 非功能需求

| 类别 | 要求 |
|---|---|
| 移动端 | 375px 宽度起完美显示；iOS Safari 为主战场（`100dvh`、`env(safe-area-inset-*)`、输入框 `font-size: 16px` 防聚焦缩放） |
| 性能 | 首屏 LCP < 2.0s（4G）；仪表盘交互 < 200ms |
| 可用性 | 记录动作 ≤ 3 次点击；弱网提交失败要能重试 |
| 隐私 | 健康数据属敏感数据。**朋友之间也不可见**。不做第三方分析上报 |
| 安全 | 密码哈希、HTTPS、接口鉴权、输入校验（zod）、防越权（IDOR）、RLS |
| 成本 | 月成本 **¥0**（已确认），仅域名约 ¥70/年 |
| 可维护 | 新机器 3 条命令跑起来；有 `.env.example`；数据库有备份与迁移方案 |
| 数据 | 托管数据库自带备份 + 手动 CSV 导出双保险 |

## 7. 设计原则（苹果风的落地版）

1. **内容优先，装饰退后**：深色近黑背景、大字号、大量留白，让"68.4"这个数字成为页面主角。
2. **数据要用"人话"呈现**：不堆表格，用进度环、趋势线、一句解读。
3. **克制用色**：中性色为主，语义色只用少数几个，且必须**色盲友好**（不能只靠红绿区分）。
4. **动效服务于理解**：数字滚动、图表生长动画让人感知"变化"，不是炫技。
5. **玻璃质感有节制**：同屏玻璃元素 ≤ 3 个，滥用会掉帧且显廉价。

具体色值/字号/圆角见 `docs/03-设计系统.md`，原始调研见 `research/02-苹果视觉语言.md`。

## 8. 验收标准（Definition of Done）

**MVP 完成的定义**：
- [ ] 有一个 HTTPS 公网地址，手机浏览器能打开
- [ ] 能完成：注册 → 填档案 → 得到热量目标 → 记体重 → 记一顿饭 → 仪表盘正确显示
- [ ] 数据刷新页面后仍在（真的落库了）
- [ ] **第二个账号登录后看不到第一个账号的任何数据**（含直接改 URL/接口参数）
- [ ] iOS Safari 上添加到主屏幕后像 App
- [ ] 能导出 CSV
- [ ] 仓库有 README + `.env.example`，另一台电脑能跑起来
- [ ] 有部署文档，写清每一步做了什么、为什么

**学习轨道的定义**：能回答出这些问题——
- 请求从浏览器到数据库再回来，中间经过哪几层？
- 用户密码为什么不能明文存？存的是什么？
- 索引是干什么的，为什么按日期查体重需要它？
- 环境变量为什么不能提交到 Git？
- 域名、DNS、HTTPS 证书、服务器之间是什么关系？
- RLS 是在哪一层生效的？为什么光靠 API 层过滤不够？
