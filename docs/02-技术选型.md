## 0. 先解决一个冲突

两路调研给出了**不同**的技术栈建议：

| 来源 | 建议 | 它的理由 |
|---|---|---|
| 报告 01（同类项目视角） | Django + DRF + PostgreSQL + Vue3 + Chart.js | 对齐 wger，Python 生态文档全 |
| 报告 03（工程落地视角） | Next.js + Server Actions + Drizzle + Supabase + Recharts | 1-3 用户下维护税最低，单次部署 |

**仲裁结论：采用报告 03 的方案。** 理由：

1. 报告 01 自己就说"**抄 wger 的数据模型，不要抄它的 UI**"——同理，我们要抄的是它的**建模思路**，不是它的技术栈。数据模型可以跨语言移植，技术栈不行。
2. 前后端分离（Django + Vue）会带来 **CORS、双份鉴权、两次部署、两套环境变量**的维护税。对 1-3 个用户的应用，这个税换来的学习收益，不如把时间花在"写对聚合 SQL"和"把可视化做到发布会级"上。
3. 报告 02 的整套设计 Token（Tailwind v4 `@theme`）是 React 生态的，选 Django+Vue 会让设计系统方案作废重做。
4. **学习目标并没有被牺牲**：Next.js 方案里，用户依然要自己写 SQL（Drizzle）、自己做鉴权、自己设计 API、自己处理迁移和部署。少写的是胶水代码，不是核心环节。

> 如果需求方**明确想学 Python 后端**，这个结论要推翻重来（见待确认清单 Q6）。

## 2. 架构决策记录（ADR）

### ADR-001 · 采用「全栈一体化 + 托管数据库/认证」，而非纯 BaaS 或前后端分离

**决策**：Next.js App Router 承载全部业务逻辑与页面；Supabase 只提供 Postgres 与 Auth 两个能力，不碰业务。

**理由**：
- **否决纯 BaaS（前端直连数据库）**：那样永远写不到聚合 SQL，而体重趋势、7 日移动平均、热量-体重关联分析**全部依赖聚合查询**。这等于把项目最核心的技术内容外包了。
- **否决前后端分离**：见第 0 节。
- **反悔成本低**：Supabase → 自建 Postgres 只改 `DATABASE_URL`；唯一真实绑定是 Supabase Auth（约 20 行代码的替换量）。

**代价**：Server Actions 是 Next.js 特有范式，换框架要重写。

---

### ADR-002 · ORM 选 Drizzle，不选 Prisma

**决策**：Drizzle。

**理由**：Prisma 在做复杂聚合（窗口函数、CTE、`percentile_cont`）时容易退化成 `$queryRaw` 裸 SQL，等于绕过了 ORM；Drizzle 本身就是 SQL 的薄封装，`sql\`\`` 模板可以无缝混写。趋势线和移动平均都要用 `AVG(...) OVER (ORDER BY log_date ROWS 6 PRECEDING)` 这种窗口函数。

**代价**：Drizzle 生态与文档不如 Prisma 丰富，遇到问题靠读源码。

---

### ADR-003 · 数据模型借鉴 wger 的「原值 + 派生」范式

**决策**：
1. 食物库以**每 100g** 为基准存营养值；日志表**只存吃了多少克**，热量在查询期计算。
2. 体重不是一个专用表，而是**通用指标表** `measurements(category, date, value, source)`。
3. 额外增加 `daily_summary` 日汇总表，让趋势图只查一张表。

**理由**：
- 第 1 条（来自 wger `Ingredient.energy` 的 `help_text='In kcal per 100g'`）：食物库修正营养值时，**全部历史记录自动修正**。新手最常见的错误是把 kcal 直接写进日志行，导致数据永久失真。
- 第 2 条（来自 wger `Measurement` + `MetricType` 枚举）：后续加腰围、体脂、睡眠**零成本**，只加一条 category；`source=CALCULATED` 给趋势线等派生指标留位。
- 第 3 条：仪表盘每次要读 30-90 天的数据，实时聚合会随数据增长变慢。日汇总表把"每天一次聚合"摊销掉。

**代价**：食物库改营养值时，历史记录的显示值会变。→ **需要加"快照"逃生舱**：`meal_items` 上冗余一份当时的营养快照，用于"我当时以为吃了多少"的追溯。这是对 wger 方案的改进（研究报告 03 也独立提出了这点）。

---

### ADR-004 · 体重趋势默认显示 7 日移动平均，原始点降为背景

**决策**：趋势图主线 = 7 日移动平均；单日数据点弱化为小圆点；趋势判定用最近 14 天线性回归斜率，不用"今天比昨天"。

**理由**：单日体重受水分/盐分/排便影响，波动可达 ±1 kg，而真实脂肪变化每天约 0.1 kg——**噪声比信号大 10 倍**。裸折线会让新人在第 3 天就崩溃弃用。研究报告 01 的实证支撑：JMIR mHealth 2026 研究结论是"所有热量记录 App 的依从性都随时间下降"，所以**降低第 30 天之后的摩擦**才是设计目标。

---

### ADR-005 · 不使用 SF Pro，改用 `-apple-system` + Inter

**决策**：
- **不自托管 SF Pro，不用 `@font-face` 引 SF Pro 的 woff2。**
- 字体栈以 `-apple-system, BlinkMacSystemFont` 开头（这是调用访问者本机已装字体，不涉及分发）。
- Web 字体自托管 **Inter**（SIL OFL 1.1）作为非 Apple 设备的一致回退。

**理由**：SF Pro 授权原文明确禁止 —— "you may not use the Apple Font to create, develop, display or otherwise distribute any documentation, artwork, **website content** or any other work product"。Apple Design Resources License 同样口径。**在 Mac + Safari 上开发时看到的依然是真 SF Pro，视觉效果不打折**，只是不分发字体文件。

---

### ADR-006 · 中文食物库自建最小集，不爬《中国食物成分表》

**决策**：人工录入 **100–300 条**常见中式食物 + 常吃外卖；用官方能量公式校验（`kJ = 蛋白×17 + 脂肪×37 + 碳水×17 + 纤维×8`）；USDA FoodData Central（CC0，1000 req/h）作交叉校验；Open Food Facts 只作条码兜底。

**理由**：研究报告 01 核实——《中国食物成分表》是**有版权的出版物**，网络流传的 PDF/Excel 均非授权版本，公开发布等于侵权。Open Food Facts 是 ODbL 许可（**有传染性**）且限流极严（搜索 10 req/min），官方明确警告不能用于 search-as-you-type。

---

### ADR-007 · 部署 Vercel + Supabase，第 2-3 个月演练迁移到国内云

**决策**：MVP 用 Vercel Hobby + Supabase Free（月成本 **¥0**，仅域名约 ¥70/年）。在代码里**从第一天就准备好 `output: 'standalone'` 的 Dockerfile 路径**，第 2-3 个月做一次真实迁移演练：腾讯云轻量 2核2G **¥35/月** + Docker Compose + Caddy 自动 HTTPS。

**理由**：
- Vercel Hobby 条款限 **non-commercial, personal use only** —— 本项目是个人自用，符合。
- 国内用户为主的长期方案是香港/新加坡节点（¥38-55/月，**免备案**）；国内服务器必须 ICP 备案，周期 1-3 周，且境外注册商的域名不能备案。
- 迁移演练本身就是学习轨道的高价值内容（会真正理解 Docker、反向代理、证书、环境变量）。

**否决项**：Cloudflare Workers 免费档 CPU 上限 **10ms/请求**，官方称 SSR 类负载需 10-20ms/请求 → 跑不动。

## 3. 数据流（请求的一生）

```
浏览器 (iPhone Safari / PWA)
   │  ① 点击「记 200g 米饭」
   ▼
Next.js Server Action  ──② 校验入参（zod）
   │                      ③ 取当前登录用户（Supabase Auth 的 JWT → RLS 上下文）
   ▼
Drizzle ORM  ──④ 生成参数化 SQL
   │
   ▼
Postgres (Supabase)  ──⑤ RLS 策略强制 user_id 隔离 + 索引命中
   │
   ▼
⑥ 写入 meal_items → ⑦ 更新当日 daily_summary（同事务）
   │
   ▼
⑧ revalidatePath('/') → 服务端重新渲染 → ⑨ 环形进度条动效
```

**每一层都是用户要能讲清楚的知识点**：①HTTP/请求、②输入校验、③鉴权与上下文、④ORM/SQL 注入防护、⑤数据库索引与行级安全、⑥事务、⑧缓存失效、⑨前端状态更新。

### ADR-008 · 认证从「预建账号」升级为完整的多用户注册体系

**背景**：最初（研究报告 03）的建议是"后台预建 3 个账号、不做注册页"——那在"只有自己用"的前提下最省事，也最安全。但需求方确认要**拉 1-2 个朋友一起用**，这个方案作废。

**决策**：
1. 实现**完整注册流程**：邮箱 + 密码注册 → 邮箱验证 → 登录 → 忘记密码（邮件魔法链接）。
2. **数据隔离靠 Supabase RLS 在数据库层强制**，不依赖 API 层过滤。
3. 邀请制：注册时校验**邀请码**（环境变量配置）。理由：这是一个私人健康数据应用，公开可注册等于把数据库敞开门；邀请码是零成本且有效的第一道门槛。

**实际落地（2026-10，与上面三条计划有出入，如实记下来）**：

| 计划 | 实际 | 为什么改 |
|---|---|---|
| 邮箱 + 密码注册 | **魔法链接**为主（`shouldCreateUser: true`） | 密码要处理强度、找回、复用、泄露四件事，而魔法链接的凭据是一次性短时效的。对一个 3 人工具，成本换不来收益 |
| 邮箱验证 | 隐含在魔法链接里 | 点开链接本身就证明了他能收这个邮箱的信，不需要单独一步 |
| 忘记密码 | 不需要 | 没有密码就没有「忘记」 |
| 邀请码 | **未实现**（`invite_codes` 表建了但没接） | 软肋在于 `shouldCreateUser: true` —— 知道网址的人都能注册。当时判断「3 人自用」可接受，但**这个判断后来被证明是错的**，见下 |

**后来补的（2026-10，真实用户被挡在门外之后）**：加了**密码登录**这条并行的通道，和 `/settings`（改邮箱 / 改密码 / 退出登录）。触发它的不是设计上的顾虑，是一次真实的翻车：

- 用户拿 GitHub 的 noreply 地址（`xxx+用户名@users.noreply.github.com`）注册 —— 那是**只写地址，收不到任何邮件**，于是「魔法链接」这条路对他等于不存在。
- 同时发现 Supabase 自带发信对免费档有**每小时几封**的硬限制，官方也明确说它不适合生产。一旦被限流，没有密码的用户就完全进不来。

教训：**「只有一条登录路径，而那条路径依赖第三方发信」是一个单点故障**，而且它只在真实用户身上暴露 —— 本地开发时 `devUser()` 会接管，构建、类型检查、单元测试三条防线全都拦不住它。

顺带一提：邀请码这个口子至今还开着，要做的话把它接进 `signInWithOtp` 的 `shouldCreateUser` 分支（改成校验通过才允许建号）。

**为什么 RLS 是必须的，而不是"更安全一点"**：
API 层过滤（`WHERE user_id = ?`）有一个致命弱点——**只要有一个接口忘了加这个条件，数据就泄露了**，而且这种 bug 不会报错，静默泄露。RLS 把它变成数据库的硬约束：即使 SQL 里完全没写 `user_id`，Postgres 也会自动加上策略条件。这叫**纵深防御**，是安全设计的基本原则。

**代价**：RLS 策略写错会导致"明明有数据却查不出来"，调试比普通 bug 烦。需要配套写策略的测试。

**遗留决策（不阻塞）**：
- 域名：先用 `xxx.vercel.app`，有域名再绑
- 主要饮食场景（食堂/外卖/自己做）：影响食物库首批要录哪些
- git 提交身份：`user.name` / `user.email` 尚未配置
- 包管理器：本机无 pnpm，**暂定直接用 npm**（少装一个工具，npm 已够用）
