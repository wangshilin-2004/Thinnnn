# 05 · 部署

从"代码在我电脑上能跑"到"我手机能打开"，中间隔着的全是配置。这份文档按顺序记录每一步、每个值的来源、以及为什么需要它。

**目标形态**：Vercel（跑 Next.js）+ Supabase（数据库 + 登录），月成本 **¥0**。

---

## 零、先理解这台机器上发生了什么

部署的本质是：**把代码搬到一台别人的电脑上，让它一直开着。**

这句话推出三件事，后面每一步都在处理它们之一：

| 推论 | 具体表现 | 本项目的应对 |
|---|---|---|
| 那台电脑上没有你的文件 | `node_modules/` 不在、`.env.local` 不在 | Vercel 会自己 `npm install`；环境变量要在面板里重新填一遍 |
| 那台电脑上的环境和你不一样 | 时区、文件系统、有没有某个库 | 所有时间计算都显式传时区（服务器跑 UTC）；`output: 'standalone'` 注释在 `next.config.ts` 里备用 |
| 那台电脑上的东西别人也能访问 | 你的密钥、你的数据库 | 密钥只走环境变量；数据库靠 RLS 而不是靠"别人不知道地址" |

## 一、Supabase 侧配置

### 1.1 Redirect URL 白名单 ⚠️ 漏了这一步登录会失败

**位置**：Supabase 面板 → **Authentication** → **URL Configuration**

（这个页面藏在 Authentication 里面，**不在 Settings 里**，很多人找不到。直达路径是 `/dashboard/project/<你的项目ref>/auth/url-configuration`。）

要填两处：

**Site URL**：你最主要的那个地址。本项目线上是 `https://thinnnn.top`；还在本地阶段时先填 `http://localhost:3000`。

**Redirect URLs**（一行一条，原有的本地那行**不要删**）：
```
http://localhost:3000/**
https://thinnnn.top/**
https://*-wangshilin-2004.vercel.app/**
```

**为什么必须配**：魔法链接的流程是「点邮件里的链接 → 回到我们的站点」。Supabase 在**发信前**会检查回跳地址在不在白名单里，不在就拒绝。这是防钓鱼的设计 —— 否则攻击者能拿你的 Supabase 项目给用户发一封"登录"邮件，链接却指向他自己的站。

**两个字段分工不同，只改一个会留半截问题**：

- **Redirect URLs 是白名单。** 代码里传的是 `emailRedirectTo: ${origin}/auth/callback`（`src/app/login/actions.ts:96`，`origin` 从请求头 `x-forwarded-host` 实时拼出来，所以同一条代码能服务 localhost / 预览域名 / 正式域名三种情况）。Supabase 拿这个地址跟白名单比对。
- **Site URL 是兜底。** 当上面那个地址不在白名单、或者某处没传 `redirectTo` 时，Supabase 退回这个地址。它还决定「确认邮箱」「重置密码」这类邮件的默认落点。

所以只改 Site URL → 链接发出去跳转被拒；只改白名单 → Site URL 还指着旧地址，某些路径仍会跳错。

> **配错了会怎样，以及为什么还有救**
>
> 白名单没配上时，Supabase **不报错**，它把回跳悄悄换成 Site URL。
> 邮件里那条链接于是打到 `https://<域名>/?code=xxx` —— 没有任何代码处理 `code`，
> 用户看到「点完链接还是没登录」，日志里一条错误都没有。这是本项目查得最久的一个 bug。
>
> `src/proxy.ts` 里留了一道兜底：任何路径上带 `code` 就转去 `/auth/callback`。
> 所以配错了通常也能登进去。**但不要因此就不配** —— 兜底只处理魔法链接这一条路径，
> 「确认邮箱」「重置密码」那些邮件的落点仍然只看 Site URL。

**为什么用通配**：Vercel 每次部署都会给一个带随机哈希的预览域名（`thinnnn-git-main-xxx.vercel.app`），逐条加不现实，通配能覆盖所有预览部署。正式域名确定后再单独加一条精确的（本节第三条就是）。

**什么时候会踩到**：**密码登录完全不经过这里**，配不配都能登。只有「邮件登录链接」以及以后的「重置密码」依赖它 —— 所以这一步漏了，症状是「密码能进、发链接收不到/点了报错」，很容易被误判成邮件服务坏了。

### 1.2 邮件模板（可选）

**位置**：Authentication → Email Templates → **Magic Link**

默认模板是英文的。想改成中文就在里面写，可用变量 `{{ .ConfirmationURL }}`：

```html
<h2>登录轻记</h2>
<p>点下面的链接进来，15 分钟内有效：</p>
<p><a href="{{ .ConfirmationURL }}">进入轻记</a></p>
```

**顺带提醒**：Supabase 免费档自带邮件服务**限流很严**（每小时几封），而且发件人是 Supabase 的域名、很容易被判垃圾邮件。自用没问题；真要拉朋友了，换成 Resend 免费档（每天 100 封，能配自己的域名）。

### 1.3 关闭自动暴露（重要，只在建项目时能设）

三个安全开关的正确姿态：

| 开关 | 设置 | 理由 |
|---|---|---|
| Enable Data API | ✅ 开 | 零成本，且能用 curl 从外部亲眼验证 RLS 在工作 |
| **Automatically expose new tables** | ❌ **关** | 关掉后新表默认谁都访问不了，必须显式 GRANT。于是「忘了配权限」的后果从**静默返回 0 行**变成**响亮的 42501 报错**。响亮 > 静默 |
| Enable automatic RLS | ✅ 开 | 建一个 event trigger，public schema 任何新表自动开 RLS。忘开一次 = 一次真实数据泄露 |

> 如果项目已经建好了，第一项和第 2.1 节的多用户部分在 `drizzle/0005_harden_grants_and_cascade_fix.sql` 里用 REVOKE 补上了 —— 迁移文件里显式收回权限，效果一样。

## 二、Git 与 GitHub

> **本节已经做完了** —— 仓库在 https://github.com/wangshilin-2004/Thinnnn ，
> `main` 分支与本地一致。留着是为了讲清每一步在做什么，以及万一要换仓库时怎么重来。

### 2.1 配置提交身份

Git 把**每一个提交**都记上作者名和邮箱，这是永久的、会进 GitHub 贡献图的。

```bash
git config --global user.name "你的名字"
git config --global user.email "你的邮箱@example.com"
```

**邮箱建议用 GitHub 提供的隐私邮箱**（GitHub → Settings → Emails → Keep my email addresses private），形如 `12345678+用户名@users.noreply.github.com`。
理由：公开仓库的提交记录里，你的真实邮箱会被爬虫抓走用于发垃圾邮件。用了隐私邮箱，GitHub 照样能把提交算到你头上。

### 2.2 确认没有密钥要提交 ⚠️

**这一步不能跳。** 一个密钥进了 Git 历史，就算你立刻删掉，它**依然在历史里**，而且大概率几分钟内就被爬虫扫到并拿去用（挖矿、刷 API 账单）。唯一的补救是**轮换密钥**，不是删文件。

```bash
# 应该输出 .gitignore 里对应的规则，说明被挡住了
git check-ignore -v .env.local .env.development.local

# 应该输出空 —— 没有任何 env 文件被跟踪
git ls-files | grep -i env
```

本项目的 `.gitignore` 用的是**模式**而不是文件名：

```gitignore
.env*
!.env.example
```

为什么用模式：将来新增 `.env.production`、`.env.staging` 会自动受保护。如果逐个列文件名，加新文件时忘了补一行，密钥就漏了 —— **这类"忘了加"的失败模式，要靠规则本身杜绝，不能靠记性。**

`.env.example` 用 `!` 显式放行，因为它是给人看的模板，只有占位符。

### 2.3 首次提交

```bash
git add -A
git commit -m "初始提交：轻记 —— 体重与饮食可视化管理"
git branch -M main
```

### 2.4 建仓库并推上去

在 GitHub 网页上：右上角 **+** → **New repository**

| 字段 | 填什么 |
|---|---|
| Repository name | `Thinnnn`（本文档就以它为例） |
| Description | 体重与饮食可视化 · 苹果发布会风格 |
| 可见性 | **Private** 建议。（Public 也行，但 LeetCode 式的刷题仓库无所谓，这个里面有你的健康数据模型设计） |
| Initialize with README | ❌ **不要勾** —— 我们已经有一个 README 了，勾了会产生冲突，推的时候要先 pull 合并 |

创建后页面会显示推送命令：

```bash
git remote add origin https://github.com/你的用户名/Thinnnn.git
git push -u origin main
```

**认证**：第一次 push 会要你登录。GitHub 早就不接受账号密码了，要么用浏览器授权（macOS 钥匙串会存下来，最省事），要么用 Personal Access Token。

## 三、Vercel 部署

### 3.1 导入仓库

1. 打开 https://vercel.com → **Continue with GitHub**（用同一个账号，链路才通）
2. **Add New…** → **Project**
3. 找到刚推的 `Thinnnn` → **Import**

Vercel 会自动识别这是 Next.js，**构建命令和输出目录都不用改**。

### 3.2 填环境变量 ⚠️ 最容易出错的一步

在 **Environment Variables** 区域，把 `.env.local` 里的值**逐条抄进去**（本地文件 Vercel 读不到）：

| 变量名 | 值从哪来 | 备注 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Connect → App URL | 公开值，会编译进浏览器 |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase → Project Settings → API Keys → Publishable key | **公开值是设计如此** —— 安全边界在 RLS，不在这把钥匙 |
| `DATABASE_URL` | Supabase → Connect → Transaction pooler | 端口 **6543** |
| `DIRECT_URL` | Supabase → Connect → Direct connection | 端口 **5432** |
| `OWNER_EMAILS` | 你自己填，逗号分隔 | 谁能在这个站里生成邀请码。**留空 = 没人能生成**，而新用户注册必须要码，等于把注册关死。目前填的是站长邮箱 |

另外两个变量**故意不在上表**：

- `SUPABASE_SERVICE_ROLE_KEY`：`.env.example` 里留着，但**当前代码不用它**。邀请码的读写走 `drizzle` 的 `postgres` 角色（`DATABASE_URL`），那是库的属主、绕过 RLS —— 见 `src/lib/invite-admin.ts` 开头那段注释。曾试过用这把 key 打 PostgREST，结果 403 `permission denied for table invite_codes`：新格式 `sb_secret_…` 不是 JWT，PostgREST 无法据此假定 `service_role`，**连 RLS 那一层都没到就被 GRANT 挡了**。
- `DEV_USER_ID`：只在本地开发用，见 `docs/06` 的说明；线上千万不要填。

**这里有三类错误，全都会在运行时才炸，构建阶段一切正常：**

1. **密码里有特殊字符没转义。** `@ : / # ?` 必须 URL 编码，`@` → `%40`。症状是 `getaddrinfo ENOTFOUND` 或者连到一个奇怪的主机名。
2. **`DATABASE_URL` 和 `DIRECT_URL` 填反了。** 迁移是 DDL，必须走 **5432 直连**；应用查询走 **6543 连接池**。填反的症状很隐蔽：应用能跑，但偶尔报奇怪的错（连接池的 transaction 模式会把同一个事务分配到不同后端，prepared statement 因此串会话 —— 这就是 `src/db/index.ts` 里写死 `prepare: false` 的原因）。
3. **`NEXT_PUBLIC_` 前缀写错。** 少一个字母、大小写不对，变量在浏览器端就是 `undefined`。而且**不会报错**，只会表现为"登录按钮点了没反应"。改这个前缀需要**重新构建**才生效（它是在构建时被内联进代码的）。

### 3.3 部署

点 **Deploy**，等 1–3 分钟。

#### 部署前先看一眼「函数区域」

Vercel 新项目默认落在 **`iad1`（美国华盛顿）**。这个默认值对本项目是双输：

- 你在国内访问 → 每个请求白绕一趟跨太平洋
- Supabase 默认给你开的是 **`ap-southeast-1`（新加坡）** → 应用在美国、库在新加坡，一次页面渲染里那几条查询全部跨半个地球

本项目就是踩了这个坑：部署上线后查了项目设置才发现是 `iad1`，改成了 **`hkg1`（香港）**。改前没量对照数据，但拓扑上少了两趟跨洋往返，这是能算出来的账，不是感觉。

改法：**Project → Settings → Functions → Function Region**。或者用 API：

```bash
curl -X PATCH "https://api.vercel.com/v9/projects/$PROJECT_ID?teamId=$TEAM_ID" \
  -H "Authorization: Bearer $VERCEL_TOKEN" -H "Content-Type: application/json" \
  -d '{"serverlessFunctionRegion":"hkg1"}'
```

**⚠️ 改完必须重新部署一次才生效。** 区域是烘焙进每一次部署里的，不是运行时去读的 —— 改完设置不重新部署，线上还是老区域。

怎么选：库在 `ap-southeast-1` 就选 `hkg1`（离国内最近，到新加坡也近）或 `sin1`（和库同区，库往返几乎为零）。**国内用户优先 `hkg1`。**

### 3.4 部署后必做的三件事

**① 把 Vercel 域名加进 Supabase 的 Redirect URLs**

回到 1.1 节，把 `https://*.vercel.app/auth/callback` 加上（如果之前没加）。**不加的话登录一定失败** —— 发信那一步就会被 Supabase 拒绝。

**② 跑一次真库迁移**

代码部署了，但数据库结构可能不是最新的：

```bash
npm run db:migrate      # 在你本机跑，连的是真库
```

**③ 验证**

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://你的域名.vercel.app/          # 期望 200
curl -s -o /dev/null -w "%{http_code}\n" https://你的域名.vercel.app/dashboard # 期望 307（跳登录页）
```

第二个如果返回 **200 而不是 307**，说明**鉴权没生效** —— 立刻停下来查，不要继续。这通常意味着环境变量没配好，或者 `src/proxy.ts` 没被识别。

**然后去手机浏览器打开，走一遍**：登录 → 邮箱收信 → 点链接 → 填目标 → 记一餐。

### 3.5 绑定自己的域名（国内几乎是必须的）

**先解释为什么非做不可。**

`*.vercel.app` 在国内是打不开的，而且不是"慢"，是"根本连不上"。本项目实测到的两道拦截：

1. **DNS 污染。** 国内公共 DNS 把 `thinnnn.vercel.app` 解析到 `54.234.18.200` 这种八竿子打不着的地址，还会返回 `2a03:2880:f10a:83:face:b00c:0:25de` —— 带 `face:b00c` 的 AAAA 记录是污染的标志性特征。
2. **SNI 阻断。** 就算手动把域名指到真实 IP（`curl --resolve thinnnn.vercel.app:443:216.198.79.67`），TCP 能连上，TLS 握手发出 ClientHello 之后**立刻被 RST**。同一个 IP、同一个端口，换成 SNI `api.vercel.com` 就能过 —— 说明被拦的是主机名，不是 IP。

**能连上的是 Vercel 的 IP，连不上的是 `*.vercel.app` 这个名字。** 换一个自己的域名，同样的 IP 就能用了。

#### 操作步骤

**① 在 Vercel 加域名**

Project → Settings → Domains → 输入你的域名 → Add。Vercel 会告诉你该填什么 DNS 记录。

本项目（`thinnnn.top`，注册在腾讯云）实际要填的三条：

| 记录类型 | 主机记录 | 记录值 |
|---|---|---|
| A | `@` | `216.198.79.1` |
| A | `@` | `64.29.17.1` |
| CNAME | `www` | `19046496ddfb8816.vercel-dns-017.com` |

腾讯云 DNS 里主机记录填 `@` 表示根域名本身。**如果列表里有默认的 parking 记录，先删掉。**

**② 等解析生效**

一般几分钟到半小时（看 TTL）。验证的时候注意一点：**如果你本机开着代理软件，`dig`/`nslookup` 可能返回 `198.18.x.x`** —— 那是 fake-ip 段，代理把 DNS 接管了，结果不作数。要么关掉代理，要么用第三方在线工具从外部节点查。

**③ 改 Supabase 的两个地方 ⚠️ 漏了这步密码能登、邮件链接登不了**

- **Site URL** → `https://thinnnn.top`
- **Redirect URLs** → 加 `https://thinnnn.top/**`

不改的话：密码登录照常（它不经过邮件跳转），但**魔法链接会跳回旧地址**，因为 Supabase 只允许白名单里的地址当跳转目标。

**④ 重新跑一遍验证**

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://thinnnn.top/          # 期望 200
curl -s -o /dev/null -w "%{http_code}\n" https://thinnnn.top/dashboard # 期望 307
```

第二个必须是 **307**。如果是 200，说明鉴权边界没生效，别往下走。

## 四、手机上的两件事

**① 加到主屏幕**

Safari → 分享 → **添加到主屏幕**。加完之后：
- 全屏打开，没有地址栏
- 有了独立的图标和名字（`app/manifest.ts` 里配的）
- 推送通知**只在已加到主屏幕时**才可能工作（iOS 的限制）

**② iOS 上没有安装横幅**

Android Chrome 有 `beforeinstallprompt` 事件，可以弹一个"安装到桌面"的提示。**iOS Safari 没有这个事件**，只能靠文字告诉用户"点分享 → 添加到主屏幕"。这是平台差异，不是可以绕过的实现问题。

## 五、出问题时先看这里

| 症状 | 最可能的原因 |
|---|---|
| 点了登录，邮箱没收到信 | ①先看垃圾邮件箱 ②Supabase 免费档发信限流（每小时几封）③**改用登录页的「密码」标签**——那条路不依赖发信 |
| **发信被限流了，一小时内谁都进不来** | 这正是加密码登录的原因。让用户先在没被限流的时候设一个密码（`/settings` → 改密码），之后就不受发信影响 |
| **点「发登录链接」，页面毫无动静** | 这是**曾经的真实 bug**（`'use server'` 文件导出了常量对象，导致 POST 500）。现在 `npm run verify` 里的 `actions:verify` 会静态拦住它，不该再出现；若出现了，看 Vercel Functions 日志里的 `A "use server" file can only export async functions` |
| 点邮件里的链接报错 | Redirect URL 白名单里没有这个域名（1.1 节） |
| **点链接后回到登录页，表单还在，但上方有一行红字** | 这是**预期行为** —— 那行红字就是说原因（链接过期 / 已用过 / 没带验证信息）。它是客户端渲染的，`curl` 看不到，别以为是没生效 |
| **点链接后回到登录页，什么提示都没有** | 说明线上跑的是修复前的版本。重新部署一次（`CompleteSession` 组件缺失） |
| 登录后立刻被踢回登录页 | Cookie 没写进去。检查 `NEXT_PUBLIC_SUPABASE_URL` / `ANON_KEY` 是否正确 |
| 页面报 500，日志显示连接失败 | `DATABASE_URL` 的密码没 URL 编码，或者端口填成了 5432（应用应该用 6543） |
| 本地好好的，线上时间差 8 小时 | 时区问题。所有"今天是几号"都必须走 `todayInTimezone(用户时区)`，不能用服务器的 `new Date()`。Vercel 跑 UTC |
| 迁移报 `schema "auth" already exists` | 这是历史上踩过的坑 —— drizzle-kit 把 Supabase 的 `auth.users` 当成自己的表了。已在 `src/db/schema.ts` 顶部注释里记录，**不要**再声明 `pgSchema('auth')` |
| 项目放了几天打不开 | Supabase 免费档连续 **7 天无请求会暂停**。去面板点一下唤醒，数据不丢 |
| **用 GitHub 的 noreply 邮箱登录，永远收不到信** | `xxx+用户名@users.noreply.github.com` 是**只写地址，收不到任何邮件**。它适合当 git 提交身份，但**不能用来注册/登录**应用。两条出路：①用登录页的「密码」标签 ②登录后去 `/settings` → 改邮箱，换成真实地址 |
| 在 Supabase 面板里「加了用户」，登进去发现数据是空的 | **面板新建账号 = 一个全新的账号**，它看不到旧账号的数据。如果本意是「换一个邮箱继续用」，应该登录旧账号后去 `/settings` → 改邮箱（那样数据跟着走），而不是在面板建新号 |
| 改了邮箱，但登录时新地址说「不存在」 | 改邮箱是**两步**的：Supabase 会往新地址发确认信，点开它地址才真的换过去。确认信到不了的话，用密码登录旧地址再试一次 |
| 改邮箱时提示确认信发了但收不到 | Supabase 后台 Authentication → Email 里的 **Secure email change** 如果开着，会**同时**往旧地址和新地址各发一封、两边都点完才生效。旧地址是 noreply 那种收不到信的话，这个流程会永远卡住 —— 把它关掉 |
| Supabase 面板里删用户，报 `Database error deleting user` | 这是**曾经的真实 bug**（`sync_one_weight` 少了父行守护，只要用户记过一次体重就删不掉）。0007 迁移已修，确认线上库跑过 `npm run db:migrate` 即可；回归测试在 `db:verify` 的【K】节 |
| 线上库里出现 `*.example.invalid` 之类的账号 | 是 `npm run db:verify:hosted` 留下的。那个脚本会真的在线上建/删一次性账号来验 RLS，中途失败就会留下残骸。确认没在用之后直接删即可 |

### 5.1 为什么登录失败一定要显示原因

这不是装饰。登录失败最坏的形态是**界面没反应**：用户以为是自己没点到，
于是反复点「发登录链接」，然后撞上 Supabase 的发信频率限制 ——
从此连重试这条路都断了，只能等一小时。所以每一个失败分支都必须落到一句
能回答「那我现在该干什么」的话上，而不是静默重定向。

实现上有个反直觉的地方：**这段提示是客户端组件渲染的**
（`src/app/login/complete-session.tsx`），不在服务端 HTML 里。
原因是两种登录流程会在同一个 URL 上撞车 ——
PKCE 失败时路由处理器加上 `?error=nocode`，而 Supabase 有时会用隐式流程
把令牌放在 fragment 里回跳，两者同时到达的话，服务端一旦直接渲染「失败」，
用户就会先看到报错再被正确的令牌救走。所以判断统一放在客户端，令牌优先。

要验证这段逻辑，`curl` 和服务端日志都帮不上忙，得用真浏览器：

```bash
PORT=3000 node scripts/devtools/console.mjs '/login?error=nocode' 1500
PORT=3000 node scripts/devtools/console.mjs '/login#access_token=bogus' 2500
```

（`PORT` 必须传，默认连的是 3100。这个工具只在该报错时报错，可以直接用退出码判断。）

## 六、下一步：什么时候该考虑搬家

现在这套（Vercel + Supabase）月成本 ¥0，够用到很后面。搬家信号：

- **触发 Vercel Hobby 条款**：它明确写着 "non-commercial, personal use only"。开始收费就该上 Pro（$20/人/月）或搬走
- **想省钱且有运维意愿**：腾讯云轻量 2 核 2G 约 ¥35/月（香港地域免备案），Docker Compose 跑 app + postgres，Caddy 自动 HTTPS
- **要注意的**：Cloudflare Workers 免费档 CPU 上限 **10ms/请求**，官方说 SSR 类负载需要 10–20ms —— **免费档跑不动 Next.js SSR**，别被"免费"吸引过去
- **国内服务器必须 ICP 备案**（1–3 周），且境外注册商的域名不能备案

搬家时**代码几乎不用改**：解开 `next.config.ts` 里 `output: 'standalone'` 的注释，把 `DATABASE_URL` 指向新库，重跑 `npm run db:migrate`。这正是 `src/db/index.ts` 里所有连接都从环境变量读、不写死的原因。
