> 载体：Drizzle ORM + Postgres 17（Supabase 托管）

## 1. 三条设计原则（都来自对 wger 源码的实测）

### 原则一：存**原值**，不存**结论**

wger 的 `Ingredient.energy` 字段 help_text 写的是 `'In kcal per 100g'`——**食物库所有营养值统一按「每 100 克」存**，`LogItem` 只存 `amount + weight_unit`，热量在查询期换算。

初学者最常见的错误是：用户吃 200g 米饭，直接把「232 kcal」这一行写进日志表。这样一旦发现食物库某条数据录错了，**全部历史记录都是错的**，而且没法自动修复——因为原始信息（吃了多少克）已经丢失了。

**推论**：`meal_items` 必须至少存 `food_id + quantity_g`，营养值是可以从这两个推出来的派生量。

### 原则二：体重**不是**专用表

wger 把体重建成通用表 `Measurement(category × date × value)`，枚举里同时装着体重、体脂、腰围、睡眠。图表类型也已经显式枚举好：`LINE / BAR / HEATMAP / DELTA / DISTRIBUTION`。

**红利**：以后要加腰围、体脂、睡眠，**不用建新表、不用改一行查询代码**，只加一个 `metric` 值。而且"趋势图"这个组件是通用的——同一份代码能画所有指标。

### 原则三：派生数据要**物化**，但只物化一次

仪表盘每次要读 30-90 天的数据。如果每次都实时 `JOIN + GROUP BY`，随着数据增长会越来越慢。

**日汇总表**把"每天聚合一次"摊销掉。代价是要保证它和源数据一致——用**触发器**而不是应用代码，因为应用代码会漏（比如你哪天直接在 SQL 控制台改了一条记录）。

## 2. 与 wger 的一处分歧：快照 vs 活算

原则一说"存原值"，但这里有个真实的张力：

| 方案 | 含义 | 优点 | 缺点 |
|---|---|---|---|
| **活算**（wger 做法） | 仪表盘实时 `food.kcal × quantity/100` | 食物库修正后历史自动回溯 | 每次查询都要 JOIN 食物库；用户看到的历史数字会**在背后变化** |
| **快照** | 写入时算好，存进 `meal_items.kcal` | 写入后不可变；查询快；`daily_summary` 汇总成本极低 | 食物库修正后**不会**回溯 |

**我们的决策：两者都存，快照负责显示，原值负责重算。**

```
meal_items:
  food_id        ← 原值引用（用于重算 + "常吃项"推荐）
  quantity_g     ← 原值（吃了多少）
  kcal / protein_g / fat_g / carb_g   ← 快照（写入时算好，显示用这个）
  food_name / serving_label           ← 文本快照（食物被删后记录仍可读）
```

理由：**食物日记在语义上是一份历史记录**，用户第 30 天回看「我当时记了什么」，看到的东西不应该变。但 wger 的担忧也是对的——所以提供用户主动触发的**「按当前食物库重算历史记录」**操作（带预览、可撤销）。

这比任何单一方案都强：两种需求都满足，而且这个权衡本身是可以讲清楚的知识点。

## 3. ER 总览

```
auth.users (Supabase 提供)
    │ 1:1 (id)
    ▼
profiles ──────────────────────────────────────┐
    │                                          │
    │ 1:N                                      │ 1:N
    ▼                                          ▼
invite_codes (独立，无外键)              measurements
                                               │ user_id, metric, measured_on
                                               │ metric ∈ weight/body_fat/waist/…
                                               │ UNIQUE(user_id, metric, measured_on)
                                               │
                                               │ 触发器同步 metric='weight'
                                               ▼
foods ──1:N──> food_servings            daily_summary
  │  owner_id NULL = 内置                  ▲ user_id + log_date 复合主键
  │  owner_id 非空 = 用户自建               │ 冗余 weight_kg / target_kcal
  │                                        │ 触发器维护
  │ 1:N (food_id, ON DELETE SET NULL)      │
  ▼                                        │
meal_items ────────────────────────────────┘
  user_id + log_date + meal_type
  + 营养快照 + food_name 快照

food_favorites (user_id, food_id) 复合主键
```

**7 张业务表**：`profiles`、`foods`、`food_servings`、`meal_items`、`measurements`、`daily_summary`、`food_favorites`，外加 `invite_codes`。

## 4. 逐表设计

### 4.1 `profiles` — 用户档案与目标

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | ← `auth.users(id)` **ON DELETE CASCADE** |
| `display_name` | text | |
| `timezone` | text NOT NULL DEFAULT `'Asia/Shanghai'` | **关键，见 §10** |
| `sex` | text | `male` / `female` — 影响 BMR |
| `birth_date` | date | **不存 `age`** |
| `height_cm` | numeric(5,1) | CHECK 50–260 |
| `activity_level` | text | `sedentary`/`light`/`moderate`/`active`/`very_active` |
| `goal_type` | text | `lose`/`maintain`/`gain` |
| `start_weight_kg` `target_weight_kg` | numeric(5,2) | |
| `rate_kg_per_week` | numeric(3,2) | CHECK 0–1.5 |
| `bmr_kcal` `tdee_kcal` `target_kcal` | integer | 计算结果 |
| `target_protein_g` `target_carb_g` `target_fat_g` | numeric(5,1) | |
| `calc_version` | text DEFAULT `'v1'` | 公式版本号 |
| `onboarded_at` | timestamptz | NULL = 还没走完引导 |
| `created_at` `updated_at` | timestamptz | 触发器自动更新 |

**为什么存 `birth_date` 而不是 `age`**：年龄每年变一次。存 `age` 的话，用户一年后回来 BMR 就是错的，而且你永远不知道他是哪年填的。存出生日期，BMR 永远算得对。

**为什么要存算好的 `target_kcal`**：
1. 目标可能被用户手动覆盖（"系统建议 1800，我就要 1700"），覆盖后需要持久化；
2. **历史记录要用当时的目标来评判**——今天改了目标，不该让上个月的所有天数看起来都"超标"；
3. 避免每次渲染重算。

**为什么有 `calc_version`**：营养学公式会更新（Mifflin-St Jeor 可能被更好的公式取代）。存一个版本号，将来能区分"哪些用户的目标是旧公式算的"，可以批量重算。

### 4.2 `foods` — 食物库（**每 100g 基准**）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | `gen_random_uuid()` |
| `owner_id` | uuid NULL | ← `auth.users(id)`；**NULL = 系统内置** |
| `name` | text NOT NULL | 中文名 |
| `aliases` | text[] DEFAULT `'{}'` | 别名，如「米饭」「大米饭」「白饭」 |
| `pinyin` `pinyin_initials` | text | 全拼 / 首字母，支持 `mifan`、`mf` 搜「米饭」 |
| `category` | text NOT NULL | 17 个枚举值，见 `data/foods.csv` 约定 |
| `kcal` | numeric(6,1) NOT NULL | **每 100g**，CHECK 0–900 |
| `protein_g` `fat_g` `carb_g` | numeric(5,1) NOT NULL DEFAULT 0 | **每 100g**，CHECK 0–100 |
| `fiber_g` | numeric(5,1) | 可空（很多食物没有可靠数据） |
| `sodium_mg` | numeric(8,1) | 每 100g |
| `source` | text | `builtin`/`user`/`usda`/`off` |
| `source_ref` | text | 如 USDA FDC ID |
| `is_verified` | boolean DEFAULT false | 是否通过 Atwater 公式交叉验算 |
| `created_at` `updated_at` | timestamptz | |

**`owner_id` 为 NULL 表示内置数据的这个设计**，让"全局食物库"和"我的自定义食物"共用一张表：
- 查询时不用 UNION 两张表；
- RLS 策略可以用一条表达式覆盖：`owner_id IS NULL OR owner_id = auth.uid()`；
- 用户之间的自定义食物天然隔离（`owner_id` 不同）。

**`kcal` 为什么 CHECK 到 900**：纯油脂是 884–900 kcal/100g（`9 kcal/g × 100g`），这是理论上界。超过 900 一定是数据错了（最常见的是把「每份」的值填进了「每 100g」的列）。

**为什么 nutrition 值不用硬 CHECK 校验 Atwater 一致性**：含酒精饮品（酒精 7 kcal/g）和含糖醇食品（赤藓糖醇约 0.2 kcal/g）会合理地偏离 `4p+9f+4c` 公式。硬 CHECK 会把合法数据挡在门外。所以改成 `is_verified` **软标记**，由导入脚本设置。

### 4.3 `food_servings` — 常见份量（**估量换算**）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `food_id` | uuid NOT NULL | ← `foods(id)` ON DELETE CASCADE |
| `label` | text NOT NULL | 「1 碗」「1 个」「1 份」 |
| `grams` | numeric(7,1) NOT NULL | CHECK > 0 |
| `is_default` | boolean DEFAULT false | |
| `sort_order` | integer DEFAULT 0 | |

**为什么要这张表**：需求分析里的 P2（记录太麻烦）是成败分水岭。减脂新人根本不知道「200 克米饭」是多少——但知道「一碗」。

```sql
CREATE UNIQUE INDEX food_servings_one_default
  ON food_servings (food_id) WHERE is_default;
```

这是一个**部分唯一索引**（partial unique index）：只对 `is_default = true` 的行做唯一性约束。效果是「每个食物最多一个默认份量」，同时不限制其他行。用普通的 `UNIQUE(food_id, is_default)` 做不到——那样会限制每个食物只能有一个 `false`。

### 4.4 `meal_items` — 饮食记录（**扁平结构，两层不是三层**）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid NOT NULL | ← `auth.users(id)` CASCADE |
| `log_date` | **date** NOT NULL | **业务日**（按用户时区算），不是 `timestamptz` |
| `meal_type` | text NOT NULL | `breakfast`/`lunch`/`dinner`/`snack` |
| `logged_at` | timestamptz DEFAULT now() | 真实时刻 |
| `food_id` | uuid NULL | ← `foods(id)` **ON DELETE SET NULL** |
| `food_name` | text NOT NULL | 快照 |
| `quantity_g` | numeric(7,1) NOT NULL | CHECK >0 且 ≤5000 |
| `serving_id` `serving_label` | uuid / text | 快照（用户选的是「1 碗」） |
| `kcal` `protein_g` `fat_g` `carb_g` | numeric NOT NULL | **快照** |
| `note` | text | |
| `created_at` `updated_at` | timestamptz | |

**为什么是扁平的 `meal_items`，而不是 `meal_logs` + `meal_items` 两层？**

调研报告 01 的结论是「别学 wger 的 `Plan → Meal → MealItem` 三级概念」。三级结构是为**饮食计划**设计的（我要制定下周的食谱），不是为**记录**设计的（我刚吃了什么）。

两层（`meal_logs` 一餐 + `meal_items` 餐中项）的代价：每次记录多一次 INSERT 和一次 JOIN，还要处理"这一餐删空了要不要删 `meal_logs` 行"的一致性。收益：餐级备注、餐级照片。

P0 不需要餐级备注。**所以砍掉一层**，`meal_type` 直接放在 `meal_items` 上。以后真要加餐级属性，可以加一张 `meal_notes(user_id, log_date, meal_type, note)` 表，不动现有结构。

**`food_id` 为什么是 `ON DELETE SET NULL` 而不是 `CASCADE`**：用户删掉一个自建食物时，**不应该连带删掉他三个月前的饮食记录**。有了 `food_name` / 营养快照，记录依然是完整可读的，只是失去了"重新计算"的能力。

### 4.5 `measurements` — 通用指标（**体重不是专用表**）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid NOT NULL | CASCADE |
| `metric` | text NOT NULL | `weight`/`body_fat`/`waist`/`chest`/`hip`/`arm`/`thigh`/`neck`/`sleep_hours`/`steps` |
| `measured_on` | date NOT NULL | |
| `value` | numeric(7,3) NOT NULL | |
| `unit` | text NOT NULL | `kg`/`%`/`cm`/`h` |
| `measured_at` | timestamptz | 精确时刻（早上空腹 vs 晚上，差异可达 1kg） |
| `source` | text DEFAULT `'manual'` | `manual`/`calculated`/`imported` |
| `note` | text | |

```sql
CREATE UNIQUE INDEX measurements_user_metric_date_uniq
  ON measurements (user_id, metric, measured_on);
```

**这个唯一索引直接实现了需求 F3 的「同一天重复记录 → 覆盖」**，配合 `ON CONFLICT (user_id, metric, measured_on) DO UPDATE`。

**`source = 'calculated'` 是给派生指标预留的**：比如"7 日移动平均体重"、"周环比变化"这类计算出来的值。现在不写，但枚举里留了位——这是从 wger 的 `MeasurementSource` 枚举学来的。

### 4.6 `daily_summary` — 日汇总（**为差异化图表服务**）

| 列 | 类型 | 说明 |
|---|---|---|
| `user_id` `log_date` | uuid + date | **复合主键** |
| `intake_kcal` | numeric(8,1) DEFAULT 0 | 触发器维护 |
| `protein_g` `fat_g` `carb_g` | numeric(7,1) DEFAULT 0 | 触发器维护 |
| `item_count` | integer DEFAULT 0 | |
| `weight_kg` | numeric(5,2) | **从 measurements 冗余** |
| `target_kcal` | integer | **那天的目标快照** |
| `updated_at` | timestamptz | |

**关键设计：`weight_kg` 冗余进来，让核心差异化图表只需扫一张表。**

「热量摄入 vs 体重趋势」这张图（本项目的差异化立足点）需要两条时序：每日热量、每日体重。如果不冗余，查询要 `FULL OUTER JOIN` 两张表再排序；冗余之后就是一句：

```sql
SELECT log_date, intake_kcal, weight_kg
FROM daily_summary WHERE user_id = $1 AND log_date >= $2
ORDER BY log_date;
```

一次顺序扫描（走 `(user_id, log_date)` 主键索引），没有 JOIN，没有 GROUP BY。

**`target_kcal` 为什么要快照**：用户的目标会变。如果存的是"当前目标"，那用户今天把目标从 1800 改成 2000，历史曲线会整条变形——上个月看起来天天"没吃够"。存快照，历史就是历史。

**触发器不能覆盖 `weight_kg` / `target_kcal`**：重算营养汇总的 `ON CONFLICT DO UPDATE` 只列营养列，不列这两列（见 §5.1 的 SQL）。

### 4.7 `food_favorites` — 常用食物

```sql
CREATE TABLE food_favorites (
  user_id uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  food_id uuid NOT NULL REFERENCES foods(id) ON DELETE CASCADE,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, food_id)
);
```
复合主键天然保证不重复收藏，且 `(user_id, food_id)` 索引直接服务「我的收藏列表」查询。

> **「最近常吃」不建表**——它是从 `meal_items` 派生的，用窗口函数实时算：`ROW_NUMBER() OVER (PARTITION BY food_id ORDER BY MAX(log_date) DESC)`。这是很好的窗口函数教学案例，见 §6.3。

### 4.8 `invite_codes` — 邀请码（ADR-008）

| 列 | 说明 |
|---|---|
| `code` | text PRIMARY KEY |
| `note` | 备注（给谁用的） |
| `max_uses` | integer DEFAULT 1 |
| `used_count` | integer DEFAULT 0 |
| `expires_at` | timestamptz 可空 |

**这张表 RLS 开启但「一条策略都不建」**——这是 Postgres RLS 的默认拒绝（deny by default）语义：没有策略 = 谁都不许访问。只有服务端用 `postgres` 角色（绕过 RLS）能读写。这是"最小权限"原则最直接的示范。

## 5. 触发器：保证派生数据一致

### 5.1 饮食汇总

```sql
CREATE OR REPLACE FUNCTION public.refresh_daily_summary(p_user uuid, p_date date)
RETURNS void
LANGUAGE sql
SECURITY DEFINER
SET search_path = ''
AS $$
  INSERT INTO public.daily_summary
    (user_id, log_date, intake_kcal, protein_g, fat_g, carb_g, item_count)
  SELECT
    p_user, p_date,
    COALESCE(SUM(kcal), 0), COALESCE(SUM(protein_g), 0),
    COALESCE(SUM(fat_g), 0), COALESCE(SUM(carb_g), 0),
    COUNT(*)
  FROM public.meal_items
  WHERE user_id = p_user AND log_date = p_date
  ON CONFLICT (user_id, log_date) DO UPDATE SET
    intake_kcal = EXCLUDED.intake_kcal,
    protein_g   = EXCLUDED.protein_g,
    fat_g       = EXCLUDED.fat_g,
    carb_g      = EXCLUDED.carb_g,
    item_count  = EXCLUDED.item_count,
    updated_at  = now();
$$;
```

**三个关键点**：

1. **`INSERT ... SELECT` + 聚合函数在源表为空时仍然返回一行**（全 NULL/0）。所以删光某天的记录后，汇总行会被更新成全 0 而不是消失——图表不会出现"空洞"。

2. **`DO UPDATE` 里故意不写 `weight_kg` 和 `target_kcal`**。写上就会用 `EXCLUDED`（即 NULL）把它们清空。这是一个非常容易犯的错。

3. **`SECURITY DEFINER` + `SET search_path = ''`**：触发器函数需要写 `daily_summary`，而触发它的用户可能没有该表的写权限。`SECURITY DEFINER` 让函数以定义者（表所有者）身份运行来绕过这个限制。
   但 `SECURITY DEFINER` 有经典的安全陷阱：如果 `search_path` 可被攻击者控制，他就能用同名函数劫持调用。**标准防御就是 `SET search_path = ''` 并在函数体内全部写全限定名**（`public.xxx`）。这里两者都做了。

挂钩子：

```sql
CREATE TRIGGER meal_items_sync_summary
AFTER INSERT OR UPDATE OR DELETE ON public.meal_items
FOR EACH ROW EXECUTE FUNCTION public.trg_meal_items_sync_summary();
```

`trg_meal_items_sync_summary()` 是 `plpgsql`，对 `TG_OP` 分派：`DELETE` 用 `OLD`，其余用 `NEW`；`UPDATE` 时如果 `log_date` 变了，**两天的汇总都要重算**。这个细节很容易漏。

### 5.2 体重同步

```sql
CREATE OR REPLACE FUNCTION public.trg_measurements_sync_weight()
RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER SET search_path = ''
AS $$
BEGIN
  IF (TG_OP = 'DELETE' OR TG_OP = 'UPDATE') AND OLD.metric = 'weight' THEN
    -- 重算旧日期的体重（可能是删除/改期）
    PERFORM public.sync_one_weight(OLD.user_id, OLD.measured_on);
  END IF;
  IF TG_OP <> 'DELETE' AND NEW.metric = 'weight' THEN
    INSERT INTO public.daily_summary (user_id, log_date, weight_kg)
    VALUES (NEW.user_id, NEW.measured_on, NEW.value)
    ON CONFLICT (user_id, log_date) DO UPDATE SET
      weight_kg = EXCLUDED.weight_kg, updated_at = now();
  END IF;
  RETURN NULL;
END $$;
```

### 5.3 `updated_at` 自动维护

通用函数 `public.touch_updated_at()`，挂在 `profiles`、`foods`、`meal_items`、`food_servings` 上，`BEFORE UPDATE` 时把 `NEW.updated_at = now()`。

**为什么不用 `DEFAULT now()` 就完事**：`DEFAULT` 只在 INSERT 时生效。UPDATE 时如果你不显式写 `updated_at`，它就永远停在创建时间。

## 6. 索引策略

索引不是越多越好——每个索引都会**拖慢写入**并**占用空间**。只建查询真正需要的。

### 6.1 已规划的索引

| 表 | 索引 | 服务的查询 |
|---|---|---|
| `meal_items` | `(user_id, log_date DESC)` | 仪表盘读最近 N 天 / 某天详情 |
| `meal_items` | `(user_id, food_id, log_date DESC)` | 「最近常吃」窗口函数 |
| `measurements` | **UNIQUE** `(user_id, metric, measured_on)` | 体重序列 + 同日覆盖 |
| `daily_summary` | **PK** `(user_id, log_date)` | 热量×体重双轴图 |
| `foods` | `(category)` | 分类浏览 |
| `foods` | GIN `(aliases)` | 别名搜索 |
| `foods` | `(owner_id) WHERE owner_id IS NOT NULL` | 我的自定义食物 |
| `food_servings` | **UNIQUE** `(food_id) WHERE is_default` | 默认份量唯一 |
| `food_servings` | `(food_id, sort_order)` | 列出一个食物的份量 |
| `food_favorites` | **PK** `(user_id, food_id)` | 收藏列表 |

### 6.2 为什么列顺序是 `(user_id, log_date)` 而不是 `(log_date, user_id)`

B-tree 索引遵循**最左前缀原则**：只有查询条件包含索引最左边的列时，索引才可能被用上。

我们的**每一条**查询都带 `user_id`（多用户隔离是硬要求），所以 `user_id` 必须放最左。`log_date` 放第二列，范围扫描 `log_date >= '2026-10-01'` 才能用上索引的有序性。

反过来 `(log_date, user_id)`：虽然也能支持"查所有用户某天"，但我们**永远不做这个查询**。索引白建。

> **可以验证的教学点**：在 psql 里对同一张表分别建两种索引，跑 `EXPLAIN ANALYZE` 对比，能看到一个走 `Index Scan`、一个走 `Seq Scan`。

### 6.3 「最近常吃」的窗口函数

```sql
SELECT food_id, food_name,
       COUNT(*)                            AS times,
       MAX(log_date)                       AS last_eaten,
       ROW_NUMBER() OVER (
         ORDER BY MAX(log_date) DESC, COUNT(*) DESC
       )                                   AS rn
FROM meal_items
WHERE user_id = $1
GROUP BY food_id, food_name
ORDER BY rn
LIMIT 12;
```

`ROW_NUMBER() OVER (ORDER BY MAX(log_date) DESC, COUNT(*) DESC)` —— 在**聚合结果之上**做窗口排序。这是 `GROUP BY` 和窗口函数同时出现时的执行顺序问题（先 GROUP BY 聚合，再在结果集上开窗），是 SQL 里最容易搞混的地方之一。

## 7. 行级安全（RLS）

### 7.1 为什么 RLS 是必须的，而不是"更安全一点"

**威胁模型**：Supabase 项目默认会把 `public` schema 通过 PostgREST 暴露成 REST API，而 `anon` key 是**公开的**（它必然出现在浏览器里）。

也就是说，只要 RLS 没开对，任何人拿到你的 anon key（打开网页源码就能看到）就能：

```
GET https://<project>.supabase.co/rest/v1/meal_items?select=*
```

拿到**全库所有人的健康数据**。

而 API 层过滤（`WHERE user_id = ?`）有一个致命弱点：**只要有一个接口忘了加这个条件，数据就泄露了，而且不报错**——静默泄露，你永远不会发现。

RLS 把这件事变成数据库的硬约束：即使 SQL 里完全没写 `user_id`，Postgres 也会自动给每条查询加上策略条件。

**这就是纵深防御**：应用层过滤是"我们记得加"，RLS 是"数据库不允许不加"。

### 7.2 策略模板（四类操作要分别声明）

Postgres RLS 的一个常见误解是以为 `CREATE POLICY ... FOR ALL` 就够了。实际上 `FOR ALL` 里 `USING` 和 `WITH CHECK` 的语义不同：

- `USING`：**这一行你能不能看见**（SELECT / UPDATE / DELETE 的过滤条件）
- `WITH CHECK`：**你写进去的这行合不合法**（INSERT / UPDATE 的校验条件）

INSERT 没有 `USING`（还没有旧行），DELETE 没有 `WITH CHECK`（没有新行）。

```sql
ALTER TABLE public.meal_items ENABLE ROW LEVEL SECURITY;

CREATE POLICY meal_items_select_own ON public.meal_items
  FOR SELECT TO authenticated
  USING (user_id = (SELECT auth.uid()));

CREATE POLICY meal_items_insert_own ON public.meal_items
  FOR INSERT TO authenticated
  WITH CHECK (user_id = (SELECT auth.uid()));

CREATE POLICY meal_items_update_own ON public.meal_items
  FOR UPDATE TO authenticated
  USING (user_id = (SELECT auth.uid()))
  WITH CHECK (user_id = (SELECT auth.uid()));

CREATE POLICY meal_items_delete_own ON public.meal_items
  FOR DELETE TO authenticated
  USING (user_id = (SELECT auth.uid()));
```

> **性能细节：为什么包一层 `(SELECT auth.uid())`**
>
> `auth.uid()` 是一个读取 `request.jwt.claims` 并解析 JSON 的**稳定函数**（STABLE）。直接写 `auth.uid()`，Postgres 可能在**每一行**上都调用一次它。
>
> 包成 `(SELECT auth.uid())` 之后，它变成**不相关子查询**，Postgres 的优化器会把它**提升成一个常量**（InitPlan），整个查询只求值一次。Supabase 官方文档明确推荐这个写法，在万行级表上有数量级的差异。
>
> 这是一个"看起来无意义的括号，实际上决定性能"的典型案例。

### 7.3 `foods` 的混合可见性策略

`foods` 同时装着全局内置数据和用户自建数据，所以策略要表达"内置的大家都能看，自建的只有自己能改"：

```sql
ALTER TABLE public.foods ENABLE ROW LEVEL SECURITY;

-- 读：内置的（owner_id IS NULL）+ 自己的
CREATE POLICY foods_select_visible ON public.foods
  FOR SELECT TO authenticated
  USING (owner_id IS NULL OR owner_id = (SELECT auth.uid()));

-- 写：只能写自己的，且 owner_id 必须是自己（防止伪造内置数据）
CREATE POLICY foods_insert_own ON public.foods
  FOR INSERT TO authenticated
  WITH CHECK (owner_id = (SELECT auth.uid()));

CREATE POLICY foods_update_own ON public.foods
  FOR UPDATE TO authenticated
  USING (owner_id = (SELECT auth.uid()))
  WITH CHECK (owner_id = (SELECT auth.uid()));

CREATE POLICY foods_delete_own ON public.foods
  FOR DELETE TO authenticated
  USING (owner_id = (SELECT auth.uid()));
```

注意 `UPDATE` 策略的 `USING` 里没有 `owner_id IS NULL` —— 所以**内置食物对客户端是只读的**，改不了。这正是我们想要的：没人能通过 API 篡改公共食物库。

### 7.4 `food_servings` 的"跟随父表"策略

`food_servings` 自己没有 `owner_id`，它的可见性**继承自** `foods`：

```sql
CREATE POLICY food_servings_select ON public.food_servings
  FOR SELECT TO authenticated
  USING (EXISTS (
    SELECT 1 FROM public.foods f
    WHERE f.id = food_servings.food_id
      AND (f.owner_id IS NULL OR f.owner_id = (SELECT auth.uid()))
  ));
```

**注意**：子查询里的 `foods` **本身也受 RLS 约束**（策略是查询的一部分）。`foods` 的策略不引用 `food_servings`，所以不会无限递归。如果两个表的策略互相引用，Postgres 会直接报 `infinite recursion detected in policy` —— 这是设计多表策略时的经典地雷。

### 7.5 `daily_summary`：只读

```sql
ALTER TABLE public.daily_summary ENABLE ROW LEVEL SECURITY;
CREATE POLICY daily_summary_select_own ON public.daily_summary
  FOR SELECT TO authenticated USING (user_id = (SELECT auth.uid()));
-- 故意不建 INSERT/UPDATE/DELETE 策略
```

`daily_summary` 是**派生数据**，只能由触发器（`SECURITY DEFINER`）维护。如果允许客户端写，就会出现"汇总值和明细对不上"的脏数据。

**"不建策略" ≠ "忘了建"** —— 这是有意的 deny-by-default。

### 7.6 `profiles`

```sql
CREATE POLICY profiles_select_own ON public.profiles
  FOR SELECT TO authenticated USING (id = (SELECT auth.uid()));
CREATE POLICY profiles_insert_own ON public.profiles
  FOR INSERT TO authenticated WITH CHECK (id = (SELECT auth.uid()));
CREATE POLICY profiles_update_own ON public.profiles
  FOR UPDATE TO authenticated
  USING (id = (SELECT auth.uid())) WITH CHECK (id = (SELECT auth.uid()));
-- 不建 DELETE：账号删除走管理端（service_role）
```

### 7.7 权限收口：GRANT 是 RLS 之外**另一道独立的门**

> ⚠️ **这一节是探针第一轮跑出来的血的教训**（见 §11.2）。第一版文档**整节漏了 GRANT**，导致第一条 RLS 查询直接 `42501 permission denied`。

Postgres 的访问控制是**两道门串联**，两道都过才放行：

```
客户端查询
   │
   ├─ 门 1：GRANT   「这个角色能不能碰这张表？」  ── ✗ → 报错 42501
   │
   └─ 门 2：POLICY  「能看见表里的哪些行？」      ── ✗ → 不报错，静默 0 行
```

**`CREATE POLICY` 完全不管第一道门。** 很多人以为开了 RLS 就安全了，其实如果 GRANT 没写对，连表都进不去（报错）；反过来如果 GRANT 给了而 POLICY 忘了，就是**静默的 0 行**——看起来像"今天没数据"，可能上线几周都没人发现。

Supabase 会给 `public` schema 下的新表**自动 GRANT** 给 `anon`/`authenticated`，所以在 Supabase 上开发时你永远碰不到这个坑；但换到自建 Postgres、或者 Supabase 改了默认行为，同样的迁移脚本会全线 42501。

**结论：迁移文件里必须显式写 GRANT，不依赖任何隐式默认值。**

```sql
-- 第一道门：先把 anon 的权限全部收回（匿名用户不该碰任何业务表）
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon;
REVOKE ALL ON SCHEMA public FROM anon;

-- 第二道门：authenticated 按需授权
GRANT USAGE ON SCHEMA public TO authenticated;
GRANT USAGE ON SCHEMA auth   TO authenticated;   -- auth.uid() 需要

GRANT SELECT, INSERT, UPDATE, DELETE ON public.profiles        TO authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.foods           TO authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.food_servings   TO authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.meal_items      TO authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.measurements    TO authenticated;
GRANT SELECT, INSERT, UPDATE, DELETE ON public.food_favorites  TO authenticated;

-- 只读：派生数据只能由触发器维护
GRANT SELECT                          ON public.daily_summary  TO authenticated;

-- invite_codes：不给任何权限（RLS 开着、策略不建、GRANT 不给 = 三不沾）
```

## 8. 新用户自动建档

用户注册成功后，必须有一行 `profiles` 记录。用**数据库触发器**而不是应用代码：

```sql
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER SET search_path = ''
AS $$
BEGIN
  INSERT INTO public.profiles (id, timezone)
  VALUES (NEW.id, 'Asia/Shanghai')
  ON CONFLICT (id) DO NOTHING;
  RETURN NEW;
END $$;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();
```

**为什么不写在注册的 Server Action 里**：注册路径不止一条（邮箱密码、魔法链接、将来可能的 OAuth、管理端 `admin.createUser`）。写在触发器里，**任何**路径都会自动建档，不可能漏。`ON CONFLICT DO NOTHING` 保证幂等。

> ⚠️ **待实测**：`auth.users` 在 Supabase 里属 `supabase_auth_admin` 所有，建触发器需要足够权限。Supabase 官方文档给出的就是这个模式，但要在真实项目上验证。

## 9. 迁移文件组织

**问题**：`drizzle-kit generate` 能从 TypeScript schema 生成建表 SQL，但它**不认识** RLS、触发器、部分索引、`SECURITY DEFINER` 函数。这些必须手写 SQL。

**如果分成两套迁移工具**（drizzle-kit 管表 + 手工 psql 管策略），迟早会漂移——而且新人根本不知道要按顺序跑两遍。

**方案：用 drizzle-kit 的 custom migration 机制，保持单一迁移流水线。**

```bash
# 1. 从 TS schema 生成建表 SQL
npx drizzle-kit generate --name=init_tables

# 2. 生成一个空 SQL 文件，手写 RLS / 触发器 / 权限
npx drizzle-kit generate --custom --name=security_and_triggers
```

两者都写进同一份 `drizzle/meta/_journal.json`，`drizzle-kit migrate` **一次全部执行**，顺序有保证。

**好处**：
- 只有一套迁移命令，不可能漏跑；
- 手写 SQL 和自动生成的 SQL 在同一个目录，一眼能看到全貌；
- 每次改动都有 SQL 文件可 review、可回滚、可进 git。

**目录结构**：
```
drizzle/
  0000_init_tables.sql                      ← 自动生成
  0001_security_and_triggers.sql            ← 手写（RLS / 触发器 / GRANT / 索引）
  0002_add_slug_and_label_uniqueness.sql    ← 自动生成
  0003_seed_foods.sql                       ← 自动生成（由 CSV 导入脚本产出）
  0004_foods_integrity_checks.sql           ← 手写（CHECK 约束）
  0005_harden_grants_and_cascade_fix.sql    ← 手写（收回过度授权 + 修注销级联）
  0006_summary_target_snapshot.sql          ← 手写（target_kcal 快照语义）
  0007_fix_account_deletion.sql             ← 手写（补 sync_one_weight 的父行守护）
  meta/_journal.json                        ← 顺序与已应用记录
```

## 10. 时间与时区：一个必须现在解决的坑

**问题**：需求里到处是"今天"。但 **Vercel 的服务器跑在 UTC**。

用户在**北京时间 10 月 17 日早上 7 点**记录早餐：

```
北京时间  2026-10-17 07:00  (UTC+8)
UTC       2026-10-16 23:00
```

如果服务端用 `new Date().toISOString().slice(0,10)` 算日期，得到 **`2026-10-16`** —— 早餐被记到了**昨天**。

**解决方案**：

1. `profiles.timezone` 存用户的 IANA 时区（默认 `Asia/Shanghai`）。
2. `log_date` 用 **`date` 类型**（业务日，不带时间），用用户时区算出来。
3. `logged_at` 用 `timestamptz` 存真实时刻（审计用）。
4. 所有"今天"的计算都走一个统一函数 `todayInTz(tz)`，不允许在别处直接 `new Date()`。

**为什么 `date` 而不是 `timestamptz` 存业务日**：业务日的语义是「用户认为的那一天」，是**日历上的格子**，不是时间轴上的点。用 `timestamptz` 会把两个概念混在一起，导致每个查询都要先做时区转换——又慢又容易错。

**为什么不用 UTC 偏移量（如 `+08:00`）**：中国没有夏令时，看起来 `+08:00` 就够了。但一旦有用户在国外，或者哪天真加了夏令时地区，偏移量会随日期变化。**IANA 时区名（`Asia/Shanghai`）是唯一正确的存法**。

第一轮跑的时候，第一条 RLS 查询就死了：

```
error: permission denied for table meal_items
  code: '42501'   routine: 'aclcheck_error'
```

**原因不是策略写错了，而是文档漏了一整层。** Postgres 的访问控制是**两道独立的门**：

| 门 | 控制什么 | 缺了会怎样 |
|---|---|---|
| **GRANT**（表级权限） | 这个角色**能不能碰这张表** | 报错 `42501 permission denied` |
| **POLICY**（行级策略） | 这个角色**能看见表里的哪些行** | 不报错，**静默返回 0 行** |

`CREATE POLICY` 完全不管第一道门。**两道都过才放行。**

这个坑特别阴险的地方在于：Supabase 会给 `public` schema 下的新表**自动 GRANT** 给 `anon`/`authenticated`，所以在 Supabase 上开发时你永远碰不到这个错；但一旦换到自建 Postgres、或者 Supabase 改了默认行为，同样的迁移脚本会全线 42501。

**已补充进 §7.7**，并写进迁移文件。

> **两种失败的"手感"完全不同，值得记住**：
> - 缺 GRANT → **报错**，你会立刻发现
> - 缺 POLICY → **静默 0 行**，看起来像"今天没数据"，可能上线几周都没人发现
>
> 后者才是安全设计里真正危险的失败模式。

### 11.4 写这个脚本时踩的两个「把假阳性当通过」的坑

两个坑都很隐蔽，而且都会让**整套隔离测试全绿却什么都没测**：

**坑一：把 `tx` 从事务回调里返回出去。**
`postgres.js` 的 `sql.begin(cb)` 在 `cb` 返回时就**提交事务**，而 `set local role` 是**事务级**的 —— 提交之后角色回退成连接默认的 `postgres`（超级用户，**RLS 对它无效**）。第一版就是这么写的，10 项「通过」全是假的：查得到 B 的数据、伪造写入成功、`anon` 不受限。
→ 现在每个断言都在事务**内部**执行，并且每次都先断言 `current_user` / `auth.uid()` 真的是预期身份，否则直接抛错。

**坑二：用「有没有报错」判断一条写入被没被拦。**
两道门的失败方式完全不同（见 §11.2）：缺 POLICY 是**静默 0 行、不报错**。所以「内置食物只读」必须断言**受影响行数 == 0**（`r.count === 0`）。第二版断言 `err === null`，得出的结论是「篡改成功了」——而实际上一个字都没改。

**另一个机制值得记住**：语句报错后事务已中止，而 `postgres.js` 会在**提交时**把那个错误重新抛出来。所以「预期被拒」的用例必须让回调 `throw` 以强制 `ROLLBACK`，否则连接会带着一个半死的事务继续跑，后面所有查询都报错（现场表现是「莫名其妙地在下一段崩掉」）。

### 11.5 这一阶段修掉的真 bug：记过体重的账号删不掉

**现象**：只要用户记过一次体重，账号就删不掉。Supabase 面板和 admin API 都只回一句含糊的 `Database error deleting user` —— 看不出任何原因。

**根因**（在线数据库上用「事务内 DELETE 后回滚」复现得到）：

```
insert or update on table "daily_summary" violates foreign key constraint
"daily_summary_user_id_fkey"   (code 23503)
where: SQL function "sync_one_weight" statement 1
       SQL statement "SELECT public.sync_one_weight(OLD.user_id, OLD.measured_on)"
       PL/pgSQL function public.trg_measurements_sync_weight() line 5 at PERFORM
```

删 `auth.users` 会级联删 `measurements`，而 `measurements` 上挂着 `AFTER DELETE` 触发器 → `sync_one_weight` → upsert `daily_summary`。此时父行正处于删除中，外键校验必然失败，**整个注销事务被拖垮**。

**修法**：`refresh_daily_summary` 早在 0006 里就有这道守护（`HAVING EXISTS (SELECT 1 FROM auth.users …)`），`sync_one_weight` 漏了 —— 同一个隐患只补了一半。`0007_fix_account_deletion.sql` 补上另一半。

**为什么测试没抓到**：`tests/verify-migrations.mjs` 的【I】节**早就测过「删用户」**，但它建的用户只有 `meal_items`、没有 `measurements`，走的是被修过的那条路径，所以一直是绿的。

> **教训（比这个 bug 本身更值钱）**：一个「删用户」测试只能证明**那个用户恰好带着的那份数据**是安全的。
> 用户身上挂几个触发器，就得建几种数据形状各测一遍。
> 现在【K】节专门建「只记体重、不记餐」的账号 —— 也就是线上删不掉的那个形状。
