## 2. 值得抄作业的设计点

### 2.1 wger 的「三层分离」营养模型 —— 最值得抄

源码实测（`wger/nutrition/models/`）：

- `Ingredient`（[ingredient.py](https://github.com/wger-project/wger/blob/master/wger/nutrition/models/ingredient.py)）：`energy`（`help_text='In kcal per 100g'`）、`protein` / `carbohydrates` / `carbohydrates_sugar` / `fat` / `fat_saturated` / `fiber` / `sodium`。**所有营养值统一以「每 100g」存储**，字段名与注释直接对齐。
- `LogItem`（[log.py](https://github.com/wger-project/wger/blob/master/wger/nutrition/models/log.py)）：`datetime`（注释明确写 `Date and Time (Approx.)`）、`ingredient` FK、`amount`（Decimal）、`weight_unit` FK、`plan` / `meal` FK。
- `Meal` → `MealItem`（计划态）vs `LogItem`（实际态）分离。

**为什么重要**：日志只记「吃了多少克」，热量在查询期用 `amount × energy/100` 算。好处是——食物库修正营养值时，全部历史记录**自动修正**；不必把营养值快照冗余进每条日志。这是新手最容易设计错的地方（很多人把 kcal 直接写进日志行）。

### 2.2 wger 的通用指标模型 —— 体重只是 `Measurement` 的一种

`wger/measurements/models/measurement.py`：`Measurement(id, category, date, value, notes, source, external_id, extra_data)`
`wger/measurements/models/category.py` 里定义了 `MetricType` 枚举：`BODY_WEIGHT / BODY_FAT / LEAN_BODY_MASS / HEIGHT / BLOOD_PRESSURE_SYSTOLIC / BLOOD_PRESSURE_DIASTOLIC / HEART_RATE / RESTING_HEART_RATE / BLOOD_OXYGEN / STEPS / DISTANCE / ENERGY / SLEEP_DEEP / SLEEP_REM …`
以及 `MeasurementSource` 枚举：`USER / GOOGLE / APPLE / CALCULATED`。

**关键设计**：体重不是一个专用表，而是「指标类别 + 时间点 + 值」。加腰围、体脂、睡眠都不用改表结构，只加一条 Category。`source=CALCULATED` 则专门给「由其他数据推算出来的指标」（如 BMR/TDEE/趋势线）留位。

### 2.3 图表类型已被显式枚举

同上文件里有 `ChartType(models.TextChoices)`：**`LINE / BAR / HEATMAP / DELTA / DISTRIBUTION`**（另含动态图表机制 `wger/measurements/dynamic/`）。这等于官方给出的"体重可视化组件清单"：折线（趋势）、柱状（每日热量）、热力图（打卡密度）、delta（增减量）、分布（体重区间分布）。

### 2.4 其他可借鉴的交互

- **Waistline → Grafana**：不自研图表，把数据导给 Grafana 做仪表盘（[waistline-api](https://github.com/hippothomas/waistline-api) 提供 `grafana-datasource` topic）。
- **FitTrackee**：Chart.js + Vue3 的完整前后端分离样板，可整体照搬工程结构。
- **Tandoor**：食谱按份数分摊营养，天然适配中餐「一盘菜多人分」的场景。
- **Nightscout**：单条时间轴叠加血糖/胰岛素/碳水，多指标同屏对照——正是「体重曲线 vs 热量曲线」要的形态。
- **wger 提供 CSV 导入/导出**（`WeightCsvImportFormPreview`、`WeightCsvExportView`）：数据可迁移是自托管项目的信任基础。

### 2.5 被公开讨论过的坑

- **依从性随时间衰减是行业共性**：JMIR mHealth 2026 年研究直接给出结论——"All calorie-counting apps saw a decline in adherence over time"（[mhealth.jmir.org/2026/1/e64139](https://mhealth.jmir.org/2026/1/e64139/)）。这意味着**设计目标不是"功能全"，而是"降低第 30 天之后的录入摩擦"**。
- **付费墙引发流失**：MyFitnessPal 把条形码扫描等功能移入 Premium 后被大量用户批评，被总结为"Loyalty Tax"危机（[reviewsextractor.com 案例](https://reviewsextractor.com/case-studies/myfitnesspal-churn)、[unstar.app 评测](https://unstar.app/blog/is-myfitnesspal-premium-worth-it-paywall-app-reviews-2026)）。
- **Open NutriTracker 的 issue 区积压 200 个未关闭问题**，wger 235 个 —— 小众健康项目普遍**维护带宽不足**，说明"功能少而稳"比"功能多"更可持续。
- wger 的 `datetime` 字段注释写着 `(Approx.)`——承认用户记不准时间，**不要强制精确时间戳**。

## 3. 差异化空间

综合上表，以下是这些项目**普遍没做好**的地方，也就是本项目的立足点：

1. **视觉表现力**：全部 13 个项目的 UI 都停留在 Bootstrap/Material 的"工具感"。没有一个把数据可视化当作品来做。苹果发布会级的排版、动效、留白、大字号数字——**这个位置是空的**。
2. **减脂新手的引导式录入**：wger 要先建 Plan → Meal → MealItem 才能记一顿饭（概念层级对新手过重）；OpenNutriTracker 走另一极端，只有日记。缺少"按场景（早餐/外卖/食堂）预设、常吃项一键复用、估量辅助（手掌/碗/拳头换算克数）"的中间层。
3. **体重趋势 × 热量摄入的关联分析**：这是最明显的空白。wger 把体重放 `measurements`、饮食放 `nutrition`，两者在 UI 上**没有打通**；FitTrackee 干脆没有饮食模块；Grocy/Tandoor 没有体重。**"近 14 天热量缺口 vs 实际体重变化"这条曲线，没人做。**
4. **滚动均值与噪声处理**：体重日间波动 ±1kg 是正常的，原始折线会打击新手信心。普遍缺少 7 日移动平均、Hacker's Diet 式趋势线、以及"数据不全时不误报"的处理。
5. **中文食物数据**：所有开源项目都只对接 Open Food Facts / USDA，**中文食物覆盖极差**（详见第 4 节），这是真实且难被抄的门槛。
6. **数据主权叙事**：OpenNutriTracker 明确打"privacy"牌拿到 2.7k star，说明这个诉求有市场，但没人把它和"好看"结合起来。

## 4. 营养/热量数据源

### 4.1 USDA FoodData Central（国际基线，已验证）

来源：[fdc.nal.usda.gov/api-guide](https://fdc.nal.usda.gov/api-guide/)

- **免费额度**：默认 **1,000 requests/hour per IP**；超限后 API key 被临时封禁 1 小时，返回 HTTP 429。文档另称"如需更高限额请联系我们"。
- **DEMO_KEY** 仅用于探索：**30 requests/hour、50 requests/day**。
- **申请方式**：任何人可访问，需在 data.gov 注册获取 API key（[Sign up to obtain a key](https://fdc.nal.usda.gov/api-key-signup.html)）。Key 不得公开，仓库里泄露的 key 会被停用。
- **许可**：**public domain / CC0 1.0**，"No permission is needed for their use"，仅请求署名并告知用途。→ **免费可商用。**
- **可用端点**：`/foods/search`、`/food/{fdcId}`、`/foods`（批量按 ID）、`/foods/list`。
- 局限：以美国食品为主，中餐/中式包装食品覆盖弱。

### 4.2 Open Food Facts（开放数据，已验证）

来源：[openfoodfacts.github.io/openfoodfacts-server/api](https://openfoodfacts.github.io/openfoodfacts-server/api/)

- **限流**：**15 req/min/IP**（`GET /api/v*/product` 单产品查询）、**10 req/min/IP**（`/api/v*/search` 搜索）。官方明确警告"不要把搜索用于 search-as-you-type，很快会被封"。超过几百个产品量级要求**下载 CSV/JSONL 全量导出**（[world.openfoodfacts.org/data](https://world.openfoodfacts.org/data)）而非逐个请求。
- **认证**：读操作免认证，但必须带自定义 User-Agent（格式 `AppName/Version (ContactEmail)`）；写操作需账号登录。建议先填 [API 使用登记表](https://docs.google.com/forms/d/e/1FAIpQLSdIE3D8qvjC_zRJw1W8OmuHhsWJ_NSckiiniAHlfaVwUZCziQ/viewform)。
- **许可**：**数据库 ODbL 1.0 / 内容 DbCL 1.0 / 图片 CC BY-SA 3.0**。→ 可商用，但 **ODbL 有传染性**：若对外提供基于 OFF 数据的衍生数据库，需以同许可开放。这是必须提前决策的法律点。
- **中文覆盖**：本次实测 `world.openfoodfacts.org/api/v2/search?countries_tags_en=china` 与 `countries.json` 均返回"Page temporarily unavailable"（触发全局限流页），**中文产品具体数量未验证**。从社区页看，OFF 中国团队仍在建设中（[OFF wiki: ChinaTeam/Country Support](https://wiki.openfoodfacts.org/index.php?title=Local_Communities/ChinaTeam/Country_Support)），可判定**中文包装食品覆盖有限**。→ 结论：OFF 适合作兜底条码源，不能作为中文主力。

### 4.3 中文食物热量数据

| 数据源 | 链接 | 性质 | 商用 |
|---|---|---|---|
| **《中国食物成分表》标准版 第6版**（中国疾控中心营养与健康所，杨月欣主编，第1册 2018 / 第2册 2019） | [chinanutri.cn 官方介绍](https://www.chinanutri.cn/yyjkzxpt/yyjkkpzx/hdjl/201501/t20150115_109857.html) | **出版物，有版权**，非开放数据；网络流传的 PDF/Excel 均为非授权版本 | ❌ 需向中国疾控中心营养与健康所取得授权 |
| 能量换算公式（官方口径） | [新疆疾控公开 PDF](https://www.xjcdc.com/Upload/History/main/upload/day_20150612/201506120117475369.pdf) | 能量(kJ) = 蛋白质×17 + 脂肪×37 + 可利用碳水×17 + 膳食纤维×8 | 公式本身公开 |
| **薄荷健康开放平台** | [one.boohee.com/store/pages/cloud_agreement](http://one.boohee.com/store/pages/cloud_agreement) · [服务协议](https://api.boohee.com/open-interface/v1/string/market_page?title=boohee_ai_service_20260608) | **存在"开放平台"页面，但非公开自助 API**。第三方目录评估其为"does not publish a public developer API or open platform"，agent-readiness 0/100（[API Evangelist: Boohee](https://providers.apievangelist.com/providers/boohee/)） | ⚠️ 需商务合作，非免费 |
| **USDA GBFPD**（全球品牌食品数据库） | [GBFPD 下载指南](https://fdc.nal.usda.gov/docs/GBFPD_Documentation_and_Download_User_Guide_Apr2023.pdf) | FDC 子库，含部分国际品牌 | ✅ CC0 |

**结论（可直接执行）**：
1. **主力自建**：以《中国食物成分表》为准，人工录入 100–300 条「常见中式食物 + 常吃外卖」的最小数据集（研究生自用完全够用），并严格遵守"每 100g"基准。
2. **兜底**：条码扫码走 Open Food Facts，缺失时回退到自建表。
3. **不要**把《中国食物成分表》的完整数据爬下来公开分发——那是版权内容，公开发布等于侵权。
4. 商用 API 备选（额度均未在本次调研中一手验证，标为**未验证**）：Edamam 最低 $14/月（100,000 calls/月，50 req/min，**要求署名且禁止缓存**，见[官方定价页](https://developer.edamam.com/food-database-api)）；Nutritionix 官网当前显示"temporarily offline while we roll out major upgrades"，免费额度与定价**未验证**。
5. **Edamam 的"禁止缓存 + 强制署名"条款意味着它不适合做本项目的长期数据底座**——一旦用户记录依赖它，付费和合规风险都不可控。

## 5. 参考产品（非开源）

| 产品 | 差异化定位 | 可视化做法 |
|---|---|---|
| **Apple 健康** | 系统级数据汇聚，不做饮食录入，只做"所有健康数据的统一视图" | iOS 27 重做版核心是 **Insights 标签页**（Heart / Sleep / Readiness / Fitness / Vitals / Cycle 六类，全天滚动更新）+ **Longevity 标签页**（跨心血管、睡眠、心理、代谢、听力、营养的长期视图，含 Health Age），关键交互是"**把用户数据叠加在专家视频/文章上**"以及"**Readiness 0–10 分并展示贡献因子**"（[FoneArena 报道](https://www.fonearena.com/blog/492020/apple-new-health-sensing-system-redesigned-health-app.html)、[apfelpatient iOS 26.4](https://www.apfelpatient.com/news/ios-26-4-new-sleep-metrics-and-vital-data)）。**本项目视觉对标对象**：大留白、单色卡片、克制的高亮色 + "分数 + 因子拆解"的叙事 |

## 6. 对本项目的启示

1. **抄 wger 的数据模型，不要抄它的 UI。** `Ingredient` 每 100g 存营养 + `LogItem` 只存 `amount/weight_unit`，让食物库修正自动回溯历史；这是全表最重要的一个决策。
2. **把"体重"建成通用的 `Measurement`（category × date × value），而不是一张体重表。** 后续加腰围/体脂/睡眠零成本；并预留 `source=CALCULATED` 给趋势线等派生指标。
3. **许可证红线**：wger/FitTrackee/OFF/Nightscout 均为 **AGPL-3.0**，只能读设计思路、不能抄代码（除非本项目也 AGPL 开源）；MIT 的 Grocy/lyftr/Actual 可放心参考。Tandoor 许可不明，避开。
4. **Open Food Facts 的 ODbL 有传染性**，且官方限流极严（搜索 10 req/min），**只用作条码兜底**，不要作为主数据源。
5. **中文食物数据必须自建**：《中国食物成分表》有版权不能公开分发；自建 100–300 条"常吃项"最小集，用官方能量公式校验（蛋白质×17 + 脂肪×37 + 碳水×17 + 纤维×8 kJ）。USDA FDC 免费可商用（CC0，1000 req/h），作为营养字段的交叉校验源。
6. **录入摩擦是第一优先级，不是附加功能。** JMIR 研究证明所有热量 App 的依从性都会随时间下滑；对策是减少概念层级（别学前端的 Plan→Meal→MealItem 三级）、支持"常吃项一键复用"和"估量换算（拳头/碗/手掌 → 克）"。
7. **差异化就做"体重趋势 × 热量摄入"的关联视图。** 现有 13 个项目里没有一家把这两块数据打通——这是明确空白，也是本项目最该主打的图表。
8. **体重曲线默认显示 7 日移动平均，原始点降为背景散点。** 日间 ±1kg 是噪声，裸折线会劝退新手；wger 的 `ChartType` 里甚至已经预留了 `DELTA` 和 `DISTRIBUTION`，可直接借用这套图表清单（LINE/BAR/HEATMAP/DELTA/DISTRIBUTION）。
9. **视觉是这个赛道的真实空位。** 所有开源项目都是 Bootstrap 工具感，所有商业产品都把图表当装饰。苹果健康式的大留白 + 卡片 + 单色高亮，配上第 7 条的关联分析，就是本项目最锋利的一刀。
10. **技术栈建议**：Django + DRF + PostgreSQL（对齐 wger，中文生态与文档最全）+ Vue3 + Chart.js（对齐 FitTrackee 的成熟组合）+ Docker Compose 一键自托管；**数据导出 CSV 必须做**（wger/Actual 都把它当信任基础）。
