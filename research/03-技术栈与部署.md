# 体重 + 饮食可视化管理网站：技术栈与部署调研

> 调研时间：2026-10-16（Asia/Shanghai）。所有价格/额度均标注查询时间；带「需二次确认」的条目为未能直接读到官方页面（网络不可达或页面 JS 化）。
> 项目约束：1–3 个真实用户（自己 + 朋友）、必须真的能上线、要完整体验前后端全链条、手机端每天高频录入、视觉对标苹果发布会。

---

## 1. 架构选型：三条路线

| 维度 | A. 一体化（Next.js App Router + Server Actions + Postgres） | B. 前后端分离（React/Vite + FastAPI 或 NestJS + Postgres） | C. BaaS（Supabase / Appwrite / PocketBase） |
|---|---|---|---|
| 开发体验 | 一个仓库、一套类型、一个 `git push`；Server Actions 省掉 API 层样板。缺点是 App Router 的 RSC/缓存心智负担真实存在 | 契约清晰、调试边界清楚；但要自己写 CORS、鉴权中间件、DTO/校验、两套部署、两套日志，1–3 用户的收益极低 | 上手最快，SDK 直连数据库，实时订阅/存储/鉴权全部现成 |
| 学习价值 | 中高：SQL、迁移、服务端渲染、部署全都能碰到，但业务逻辑高度依赖框架魔法 | 最高：HTTP 语义、鉴权、分层、独立部署全都手写一遍。适合"就是要走一遍全链条"的目标 | 最低：你在学 SDK，不是在学后端。数据库设计能力保留，服务体系能力几乎为零 |
| 部署难度 | 低（Vercel 一条流水线），或自建 VPS 用 Docker 一个容器 | 中高（2 个服务 + 反代 + 跨域），自建时最累 | 最低（前端静态托管 + 云端后端） |
| 免费额度 | Vercel Hobby 免费但**仅限非商用个人项目**；数据库需另找 | VPS 自建，¥35/月起 | Supabase Free：500 MB 库 / 5 GB 出网 / 50,000 MAU / 2 个项目，**7 天不活跃自动暂停** |
| 长期成本 | Vercel Pro $20/人/月起 才可商用 | VPS 固定 ~¥35–55/月 | Supabase Pro $25/月起 |
| Vendor lock-in | 低（Next.js 可搬去任何 Node/Docker 环境） | 最低 | 中高（Supabase 的 RLS/Auth/Edge Function 迁移成本最高；PocketBase 可整库搬走） |

关键出处：
- Vercel Hobby 明确写着 "the Hobby plan restricts users to non-commercial, personal use only"（[Vercel Hobby Plan](https://vercel.com/docs/plans/hobby)，页面 last_updated 2026-09-14）。
- Supabase 免费版额度与「7 天低活跃自动暂停」见 [Supabase Pricing](https://supabase.com/pricing) 与 [Project Pausing](https://supabase.com/docs/guides/platform/free-project-pausing)（查询于 2026-10-16）。
- Neon Free：100 CU-h/项目、1 GB 存储/项目、5 分钟无活动自动 scale-to-zero，且是**永久免费非试用**（[Neon Pricing](https://neon.com/pricing)，查询于 2026-10-16）。

### 推荐：A 为主干 + C 只做数据库/认证（混合式）

**推荐 A（Next.js App Router + Server Actions），但不要用 Vercel 的托管 Postgres，而是把 Postgres + Auth 交给 Supabase Free，业务代码全部自己写。**

理由：
1. **符合"全链条"**：数据建模、迁移、服务端聚合查询、鉴权、部署这些真正有价值的部分都由你写；Supabase 只承担"托管 Postgres + 用户表"这一层，等价于租了一台数据库，不构成"平台替你写后端"。
2. **符合"真的能上线"**：1–3 个用户下 Next.js 单进程 + 一个托管 Postgres 是最少活动部件的方案。Vercel Hobby 免费且够用（5 GB 流量/4 CPU-h/1,000,000 次调用，[同上](https://vercel.com/docs/plans/hobby)），因为纯个人使用不触发商用条款。
3. **B 的代价不划算**：FastAPI + React 双部署在这个规模下只会带来 CORS、双份鉴权、双份环境变量的维护税，学习收益在第二次部署时就衰减完。若确实想练后端分层，可以在 Next.js 里显式分出 `services/` 层——不牺牲全链条学习。
4. **纯 C 不可取**：前端直接 `supabase.from('meals').select()` 意味着你永远不会写一条真正的聚合 SQL，而趋势图恰恰全靠聚合 SQL。

**反悔成本**：Supabase → 自建 Postgres 只需改 `DATABASE_URL`；Next.js → Docker/VPS 只需一个 `Dockerfile`（`output: 'standalone'`）。唯一真正绑定的是 Supabase Auth，最多 20 行代码的替换量。**所以先按 A+C 做，第 3 个月再决定要不要搬到自购 VPS。**

## 2. 数据库与 ORM

### Postgres 托管选择

| 方案 | 关键数字 | 结论 |
|---|---|---|
| **Supabase** | Free 500 MB / 5 GB egress / 50K MAU；7 天低活跃暂停（邮件预警，暂停后 1 年内可恢复）；Pro $25/月 | **推荐**。免费版唯一实质风险是暂停，可挂一条每日 cron ping 规避；同时白送 Auth，省掉一个章节的工作量 |
| Neon | Free 100 CU-h/项目 + 1 GB/项目，**永久免费、自动 scale-to-zero**，无"暂停"概念 | 很好的 Plan B。若你更想练 Auth.js/Better Auth，Neon 的免费模型比 Supabase 更干净 |
| Railway / Render | 无真正免费档（见 §6） | 对"永远免费"不成立 |
| 自建 Docker（同 VPS） | 与 App 同机，零额外月费 | 最终形态；备份要自己写 `pg_dump` + 异地同步 |

### ORM 推荐：Drizzle

- **Drizzle**：TypeScript-first、无代码生成步骤、SQL-like API、打包体积小、原生支持 `sql` 模板写窗口函数/CTE，connection pooler 友好。适合"我既要类型安全，也想知道最终 SQL 长什么样"。
- **Prisma**：DX 与迁移工具链最成熟（`prisma migrate`），但需 codegen、引擎较重、复杂聚合容易退化成 `$queryRaw`。如果你更看重"迁移自动化"而非"控制感"，它仍合理。
- **SQLAlchemy 2.0**：只在选 B 路线（Python 后端）时考虑，否则等于引入第二语言栈。
- **裸 SQL + `postgres.js`**：学习收益最高，但迁移管理要自己写。研究生个人项目可以接受，前提是你愿意维护 `migrations/*.sql`。

**结论：Drizzle + Supabase Postgres**（连接用 Transaction Pooler 端口，避免 serverless 连接爆炸）。

### 体重/饮食时序数据的表设计要点

核心矛盾：趋势图要按天/周聚合，而明细表会随时间线性增长。1–3 个用户下数据量永远不会大（每天 <20 行，十年 <10 万行），**所以不要过早分区**，但结构要一开始就设计对：

1. **所有时间列用 `timestamptz`，另存一个 `log_date date`（用户本地时区）**。聚合按 `log_date` 走，避免每次查询都 `AT TIME ZONE`，也避免"凌晨 1 点记的算哪天"这类争议。
2. **体重表按"一天一条"建模**：`weight_logs(user_id, log_date, weight_kg numeric(5,2), measured_at timestamptz, note)`，`UNIQUE (user_id, log_date)` + `ON CONFLICT DO UPDATE` 天然实现"一天只记一次，重记即覆盖"。
3. **饮食拆成两层**：`meals(user_id, log_date, meal_type, eaten_at, photo_url)` 与 `meal_items(meal_id, food_id, grams, kcal, protein_g, carb_g, fat_g)`。营养值**冗余存在 `meal_items` 里**（记录当时的快照），否则改一次食物库就会污染历史数据。
4. **聚合用"日汇总表 + 物化视图"而非实时扫明细**：建 `daily_summary(user_id, log_date, kcal_in, protein_g, ..., weight_kg)`，写入时用触发器或 Server Action 幂等 upsert 维护。趋势图只查这一张表，行数 = 天数。
5. **索引**：`(user_id, log_date DESC)` 复合索引覆盖 99% 查询；若将来真到百万行，再按 `log_date` 上 BRIN 或按月分区（PGConf.US 2025 的时序实践结论是 BRIN 适合只追加的时序列，见 [Mastering Time-Series Data in PostgreSQL](https://postgresql.us/events/pgconfus2025/sessions/session/1970/slides/193/PGConf.US-NYC_Mastering%20Time-Series%20Data%20in%20PostgreSQL.pdf)）。
6. **趋势计算放 SQL 不放 JS**：7 日/30 日移动均值用 `avg(...) OVER (ORDER BY log_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)`，一条查询返回整条曲线，前端零计算。

## 3. 认证方案

| 方案 | 1–3 用户场景下的评价 |
|---|---|
| **Supabase Auth** | **推荐**。免费、内置 magic link + OAuth、行级安全（RLS）可在数据库层强制"只能看自己的数据"，这是三个方案里唯一把隔离做进数据库的。代价是绑 Supabase |
| Clerk | 免费档 50,000 MRU/应用、3 个 dashboard seat、$25/月起（[Clerk Pricing](https://clerk.com/pricing)，查询于 2026-10-16）。DX 最好，但免费额度对 3 个用户是巨大浪费，且引入外部依赖换 UI 组件不划算 |
| Auth.js / NextAuth v5 | 免费、无 vendor。但 v5 配置项多、OAuth Provider 与 Adapter 的状态在 2025–2026 反复变动，1–3 用户下属于"用复杂度换自由" |
| Better Auth | 2026 年社区热度上升、TypeScript-first、自带 magic link 与组织能力，可自托管在同一个 Postgres。若不想绑 Supabase，这是首选替代 |
| 极简自建 JWT / 魔法链接 | 需要自己实现 token 签发、过期、撤销、邮件发送、防重放、CSRF。**不推荐**：这是最容易写出安全事故的一块，且学习收益远低于其风险 |

**结论：直接用 Supabase Auth 的魔法链接（Magic Link）+ RLS 策略。** 三个用户，不做注册页面，直接在 Supabase 后台预建三个账号，前端只留邮箱登录。这样你既拿到工业级安全，又把精力留给可视化。

## 4. 图表与前端可视化库

| 库 | SSR 兼容 | 体积/性能 | 定制自由度 | 结论 |
|---|---|---|---|---|
| **Recharts** | 需要 `'use client'` + `dynamic(..., {ssr:false})`；本质是 D3 之上包 React 组件 | 中等，按需 import 单图后 gzip 约 40–90 KB；SVG 渲染，几百点无压力 | 中：改颜色/标签/自定义 tooltip 很方便，改布局要跟它的组合式 API 斗 | **推荐**。这个项目的图表类型（折线趋势、目标带、柱状热量、环形宏量占比）它全支持，苹果风需要的"少即是多"用它的 `CartesianGrid` 全关 + 自绘配色两周就能调出来 |
| ECharts | 非 React 原生，要自己包一层 ref 容器 | 最大（全量 >300 KB gzip，按需构建可降到 ~100 KB） | 最高，且移动端触摸交互（缩放、拖拽区间）开箱最好 | 备选。只有当你真的要做"手指拖拽查看某天详情"这类交互时才值得换 |
| visx | 纯 SSR 友好（低层 primitive） | 最小（按需引入 d3 子模块） | 最高，等于自己写图表 | 学习价值最高、交付速度最慢。**不建议用在 MVP** |
| Tremor | 服务端组件友好、自带苹果风默认样式 | 中 | 最低（本质是 Tailwind 预设组件） | 想一周内出"看起来很贵"的界面可以用它起步，但会被它的样式语言锁住 |

**结论：Recharts + 动态导入 + 只在图表区域 `'use client'`。** 移动端优先意味着首屏 JS 越小越好，把整个图表包懒加载可省下首屏 100 KB 左右。视觉上的"苹果发布会感"来自留白、字重对比、以及克制的动效（`framer-motion` 只用于数值滚动和页面切换），不来自图表库本身。

## 5. 移动端体验（PWA + iOS 的坑）

**MVP 必需**：`manifest.webmanifest`（`name` / `short_name` / `icons` 192+512 / `display: standalone` / `start_url` / `theme_color`）+ 一个最小 service worker（缓存 app shell，静态资源 stale-while-revalidate，**API 请求一律 network-only**）+ `apple-touch-icon`。iOS 26 起"添加到主屏幕"默认以 web app 打开，安装门槛已降到零（[PWAs on iPhone, 2026-10](https://dev.to/wavx_solutions_1c671328ad/pwas-on-iphone-what-works-and-what-does-not-october-2026-5cgf)）。

**iOS Safari 必须提前处理的坑**：
1. **100vh 问题**：用 `100dvh`（或 `min-h-dvh`），不要用 `100vh`；配合 `env(safe-area-inset-bottom)` 给底部固定按钮加 padding，否则灵动岛/Home 指示条会盖住"保存"按钮。
2. **输入框缩放**：`<input>` 字号 < 16px 时 Safari 聚焦会自动放大整页且不回弹。**所有输入框 `font-size: 16px`**，这一条比任何 viewport 配置都管用。
3. **固定定位**：iOS 26 Safari 出现过 `position: fixed/sticky` 元素整体位移的布局回归（[StackOverflow](https://stackoverflow.com/questions/79753701/ios-26-safari-web-layouts-are-breaking-due-to-fixed-sticky-position-elements-g)），"保存"按钮尽量放在文档流内或用 `dvh` 布局，减少对 `fixed` 的依赖。
4. **PWA 的硬限制**：没有 `beforeinstallprompt`（必须教用户"分享 → 添加到主屏幕"，检测 `display-mode: standalone` 后给一次性提示）；**没有 Background Sync / Periodic Background Sync**，离线队列只能在前台 flush；Web Push 仅在已安装为 Home Screen web app 时可用，且**每条推送必须展示通知，否则 Safari 会撤销权限**；Web Bluetooth / NFC / USB 全部不支持（同上链接）。
5. **存储**：`navigator.storage.persist()` 可申请持久化，但 Safari 有 7 天未交互清理脚本可写存储的策略（对已安装的 web app 有独立计数，风险较低）。**结论：本地只做缓存，真相永远在 Postgres。**

### 关键约束：Cloudflare Workers 免费档 CPU 只有 10 ms/请求

官方明确写 "Heavier workloads that handle authentication, server-side rendering, or parse large payloads typically use 10-20 ms"。也就是说**免费档跑不动 Next.js SSR**（OpenNext 适配器虽有，但渲染一个页面就可能超 10 ms）。结论：**Cloudflare 只适合放纯静态产物（Vite/Nuxt 静态导出）或 Hono 风格的极薄 API，不适合本项目的 SSR 主站。**

### 国内可访问性与更实际的方案

- 海外方案（Vercel / Fly / Render / Railway）在国内都属于"时好时坏，且可能随时变差"，Supabase / Neon 的 API 域名同样如此。**如果使用者和朋友主要在国内，纯海外栈的日常体验是有风险的。**
- **国内服务器必须 ICP 备案**：个人备案要求备案主体与域名实名信息一致、域名注册商须为境内有资质服务商（境外注册商域名不能直接备案）、实名认证后约 3 天信息才同步到工信部；备案完成后二级域名下所有子域可正常使用（[腾讯云 ICP 备案文档](https://cloud.tencent.com/document/product/243/18905)，2025-12-17 更新）。备案周期通常 1–3 周，且**个人备案对网站内容有约束**（不可涉及经营性信息服务/论坛社区等）——一个纯个人的记录工具处于灰色但通常可通过的地带，**需二次确认你所在省份管局的现行口径**。
- **不想备案就用香港/新加坡轻量服务器**：免备案、国内直连延迟通常 30–60 ms，质量尚可接受。

**HTTPS**：**用 Caddy，一行 `yourdomain.com { reverse_proxy localhost:3000 }` 自动申请并续期 Let's Encrypt 证书**，比 Nginx + certbot 少一半配置（[Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https)）。腾讯云/阿里云控制台也提供免费 DV 证书，可作备选。

### 推荐组合

**主方案（推荐）——零月费、当天上线：**
> Next.js App Router（Server Actions）+ Drizzle + **Supabase Free**（Postgres + Auth + RLS）+ **Vercel Hobby**
> **月成本 ¥0**，只有域名 **约 ¥70/年**。前提：纯个人非商用。

**稳健方案（国内用户为主时）——推荐作为第 2 阶段：**
> 代码不动，前端加 `Dockerfile`（`output: 'standalone'`）→ 腾讯云轻量 2核2G（**35 元/月 / 约 357 元/年**，或香港地域 **38–55 元/月免备案**）→ Docker Compose 起 `app + postgres` → **Caddy 自动 HTTPS**
> **月成本 ¥35–55**，包年约 **¥357–660 + 域名 ¥70/年**。

**推荐路径：先用主方案把产品跑起来（第 1 周），第 2–3 个月再把它当"迁移演练"搬到稳健方案。** 这样你既体验了托管平台的 CI/CD，又亲手做了一遍 Docker + 反代 + 证书 + 备份——全链条学习的目标才真正闭环。

### 从本地到线上的完整流程清单

1. `npx create-next-app@latest`，开启 TypeScript + Tailwind + App Router。
2. 建 Supabase 项目，拿到 `DATABASE_URL`（用 **Transaction Pooler** 端口 6543）与 `NEXT_PUBLIC_SUPABASE_URL/ANON_KEY`。
3. Drizzle：`schema.ts` 写 `weight_logs` / `foods` / `meals` / `meal_items` / `daily_summary`，`drizzle-kit generate` + `migrate` 推到远端。
4. Supabase 后台预建 3 个用户（邮箱），写 RLS 策略：`using (auth.uid() = user_id)`。
5. 本地 `next dev` 打通"记体重 / 记一餐 / 看趋势"三条主链路，用真机 Safari 过一遍 §5 的坑。
6. 加 `manifest` + service worker + `apple-touch-icon`，真机"添加到主屏幕"验证 standalone 打开。
7. GitHub 建仓库，Vercel 一键导入，`main` 分支自动部署，环境变量在 Vercel 后台配置（`.env.local` 加入 `.gitignore`）。
8. 买域名（若走国内备案则必须在境内注册商），Vercel 里加 Custom Domain，等 DNS 生效。
9. 挂一条每日 cron（Vercel Cron 或 GitHub Actions）ping 一次 Supabase，规避免费版 7 天暂停。
10. 验证：手机 4G 打开无样式错乱、iPhone Safari 输入框不缩放、底部按钮不被安全区遮挡、PWA 离网能开、`pg_dump` 备份脚本能跑通并上传到异地。

（若走稳健方案，则第 7–9 步替换为：买轻量服务器 → 装 Docker → `docker compose up -d` → Caddy 配域名与证书 → GitHub Actions `git pull && docker compose up -d --build` → 加 `pg_dump` 每日备份 cron。）

## 7. 数据录入效率（减脂类应用的生死线）

目标：**"记一顿饭"从打开到保存 ≤10 秒**。基准现状是"搜索食物 → 填克数 → 保存"，熟练也要 25–40 秒，这就是绝大多数饮食 App 在三周后被弃用的原因。

### 手段清单（按见效速度排序）

| 手段 | 省时原理 | 归属 |
|---|---|---|
| **最近常吃（Recent）** | 80% 的饮食是重复的，列表默认展示最近 10 条 + 出现频次排序，多数情况 = 一次点击 | **MVP 必需** |
| **收藏 / 常吃（Favorites / Quick add）** | 固定组合（早餐鸡蛋+牛奶）一键补全 | **MVP 必需** |
| **组合餐 / 模板（Meal template）** | 把"我的标准早餐"存成一个可复用条目，包含多个 `meal_items` | **MVP 必需** |
| **搜索后直接给默认份量** | 食物库预先存 `default_serving`（1 个鸡蛋 / 1 碗饭），用户不改就是接受默认 | **MVP 必需** |
| **Streak 与一键复制昨天** | "和昨天一样"覆盖相当比例的日常 | MVP 加分项 |
| **本地食物库 + 客户端模糊搜索** | 离线可用、零延迟（服务端搜索在弱网下是体验杀手） | MVP 级实现细节 |
| **条码扫描**（`BarcodeDetector` / zxing-wasm + Open Food Facts） | 包装食品录入降到 3 秒，但中国预包装食品在 Open Food Facts 的覆盖率有限；iOS Safari 无原生 `BarcodeDetector`，需 wasm 版（体积与性能代价） | 迭代 |
| **拍照估算热量**（多模态模型） | 体验惊艳但误差大（±30% 以上），且每次调用有成本 | 迭代，且只作为"估算起点" |
| **语音输入**（"两个鸡蛋一杯牛奶"） | 手不离锅时的唯一解；用 Web Speech API 或录音 + ASR | 迭代，输入法是更省事的替代 |

### MVP 判定

**必做（决定留存）**：最近常吃 + 收藏 + 组合餐模板 + 默认份量 + 本地食物库 + 一次点击保存（无二次确认弹窗、无必填备注）。

**MVP 可选**："和昨天一样"、条码扫描（如果你自己常吃包装食品）。

**明确推迟**：拍照估算、语音输入、AI 营养师、社交。这些的演示价值远高于日使用价值。

**一条硬约束**：录入表单**默认折叠**高级字段（蛋白质/碳水/脂肪按食物自动带出），永远不要让用户为了记一顿饭去填 5 个数字——一旦有必填的第二屏，10 秒目标就作废。

## 8. 给这个项目的最终技术栈建议（一句话一层）

- **框架**：Next.js（App Router）+ TypeScript + Tailwind CSS，Server Actions 承载全部写操作。
- **数据库**：Postgres（Supabase Free 托管；面向国内用户时迁到轻量服务器 Docker 自建）。
- **ORM**：Drizzle ORM + drizzle-kit 迁移，聚合查询直接写 SQL 模板。
- **认证**：Supabase Auth 魔法链接 + 数据库 RLS（预建 3 个账号，不做注册页）。
- **数据建模**：`weight_logs` 按天唯一；饮食两层 `meals` / `meal_items` 并冗余营养快照；另建 `daily_summary` 日汇总表，趋势图只查它。
- **图表**：Recharts（动态导入、只在图表区域 `'use client'`），Apple 风靠留白与动效而非图表库。
- **移动端**：PWA（manifest + 最小 service worker + `apple-touch-icon`），`dvh` + `env(safe-area-inset-*)` + 输入框 16px。
- **UI 动效**：framer-motion，仅用于数值滚动与页面过渡。
- **部署**：Vercel Hobby（个人非商用，¥0）→ 进阶迁至腾讯云轻量 2核2G Docker + Caddy 自动 HTTPS（约 ¥35/月）。
- **域名/证书**：境内注册商 `.com`（约 ¥70/年，需备案）或境外注册 + Cloudflare DNS（免备案，用香港节点）；证书交给 Caddy。
- **备份**：GitHub Actions 每日 `pg_dump` → 异地对象存储。
- **录入体验**：最近常吃 + 收藏 + 组合餐模板 + 默认份量 + 本地食物库模糊搜索。
